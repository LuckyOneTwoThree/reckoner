# 11 Agent 工作流与自动化落地

> 📌 定位：本模块是整个产品方法论的**“降阻力引擎”与“自动化执行层”**。它的核心任务是将 [[10 决策内核]] 带来的严苛执行摩擦，通过大语言模型与 Agent 编排技术进行化解，让规范的流转变为后台的自动化服务。

## 为什么需要引入 Agent 工作流？

高度结构化的产品方法论（如分类的假设台账、L1-L4的证据要求、严格的卡口放行）在纯靠人力的团队中必定遭遇极高的**执行摩擦**。
将方法论 Agent 化的本质，是把 PM 从“**表单填写者、规则背诵者**”解放为“**审批者、决策编辑者**”。

以下是本方法论配套的四个核心 Agent 工作流（可以直接作为内部工具开发的 PRD 基准）。

---

## 工作流 1：假设自动拆解与对弈 Agent

**对应解决：** [[10 决策内核]] 中“台账填写极其反人性”的痛点。

### 1.1 场景与触发
当 PM 写完一份非结构化的 PRD 草稿，或上传了一份需求会议的录音转写稿时触发。

### 1.2 Agent 执行动作
1. **意图提取**：自动提取并格式化为《产品论点 5 要素》。
2. **隐藏风险嗅探（Red Teaming）**：
   - 寻找未被验证的用户前提 -> 生成 A 类（用户）假设
   - 寻找隐性成本与转化率前提 -> 生成 B 类（商业）假设
   - 寻找性能与可行性盲区 -> 生成 C 类（技术）假设
   - 寻找隐私与安全红线 -> 生成 D 类（合规）假设
3. **代价评估**：基于内部知识库，为提取出的假设预估“错了的代价”。

### 1.3 输出与人机协作
- Agent 吐出一份《自动假设台账》草案。
- PM **不创建**台账，仅通过点击确认、修改或删除不合理假设，完成审批。

## 工作流 2：证据聚合与自动升降级 Agent

**对应解决：** [[10 决策内核]] 中“证据（L1-L4）”散落在各个系统中，无法与台账状态联动的痛点。

### 2.1 场景与触发
作为后台守护进程（Daemon），持续监听业务系统的数据流（如 Jira/TAPD 状态、Amplitude/神策看板、邮件审批记录）。

### 2.2 Agent 执行动作
1. **信号捕获与匹配**：当在邮件系统中识别到法务的“审批通过”邮件，或在数据平台抓取到实验组 p-value < 0.05 的报告。
2. **状态自动流转**：自动匹配到对应的待验证假设，将其证据强度自动提升至 `L3（强证据）`。
3. **锚点绑定**：将邮件截图或数据 Dashboard URL 作为“证据锚点”直接挂载到假设上。

### 2.3 输出与人机协作
- 满足下一阶段卡口（决策门）的所有前提条件时，Agent 自动通过 IM（如飞书/钉钉）向卡口 Owner 发送《卡口放行确认卡片》。
- 实现了卡口状态机的无人值守。

## 工作流 3：全天候洞察雷达 Agent

**对应解决：** [[02 产品探索与发现]] 中，在形成“产品论点”前，缺少对海量碎片化原始信息的收敛处理。

### 3.1 场景与触发
每日定时触发，汇总多渠道（App Store, 微博, 客服工单, 内部建议池）的非结构化原始反馈。

### 3.2 Agent 执行动作
1. **语义聚类（Clustering）**：将海量 Signal（信号）按照场景和痛点进行聚类。
2. **提炼 JTBD**：对聚类结果进行深度解读，尝试用“用户试图完成什么任务（JTBD）却遇到了什么阻碍”的格式进行归纳。
3. **阈值判定**：当某一聚类的热度达到预设阈值时，触发孵化逻辑。

### 3.3 输出与人机协作
- 自动生成一份包含原始用户原声（Quotes）引用的《新机会洞察简报》。
- PM 评估后，一键转化为正式的“产品论点”进入主循环一。

## 工作流 4：AI 评估协同 Copilot

**对应解决：** [[09 AI 产品方法论]] 中，产品经理无法直接干预模型评测（Evals）脚本，且工程师难以理解业务 Bad Case 的脱节问题。

### 4.1 场景与触发
在 AI 产品的双轨迭代中，需要新增测试用例，或发生大量线上 Bad Case 时触发。

### 4.2 Agent 执行动作
1. **正向翻译（PM -> Eng）**：
   - PM 用自然语言输入期望：“当用户询问竞品时，AI 应该委婉拒绝且不贬低”。
   - Agent 自动将其转化为 `Promptfoo` 或 `LangSmith` 标准的 LLM-as-a-judge 评估模板及 JSON 配置。
2. **逆向翻译（Eng -> PM）**：
   - 当系统出现大量差评时，Agent 抓取底层的调用 Trace 树。
   - 分析根因（是 RAG 知识库未召回、系统 Prompt 被覆盖，还是工具参数传错），并翻译为产品视角的《Bad Case 分流诊断报告》。

### 4.3 输出与人机协作
- PM 无需写任何测试代码，即可维护团队的 Golden Set。
- 产品与工程共用同一个“事实库”进行沟通，杜绝“模型智商不够”这种无效反馈。

---

## 落地建议

- **切忌贪大求全**：不要试图一次性开发四个复杂 Agent。强烈建议从 **“工作流 1：假设自动拆解与对弈 Agent”** 开始。它能提供即时反馈，立刻降低团队对新方法论的抵触情绪。
- **与工作流引擎整合**：上述能力可基于 Dify、Coze 或自研的 LangChain/LlamaIndex 框架快速实现。
