# 方法论展开

这个模块的核心命题是：​「产品永远未完成，监控与迭代是让产品持续进化的生命系统」​。是整个方法论的闭环，将所有模块串联成一个持续运转的飞轮。

---

## 模块结构总览

```
产品监控与迭代
├── 1. 监控体系建设
├── 2. 问题诊断与根因分析
├── 3. 迭代决策框架
└── 4. 产品健康度管理
```

## 1️⃣ 监控体系建设

目标：在问题影响用户之前发现它，而非被用户投诉后才知道

### 监控体系四层架构

```
业务层监控（产品是否在创造价值）
        ↑
产品层监控（功能是否被正确使用）
        ↑
性能层监控（系统是否稳定运行）
        ↑
基础设施监控（服务器 / 网络是否正常）
```

> 大多数 PM 只关注业务层——但问题往往从底层开始，PM 需要能读懂全链路信号

### 业务层监控

核心指标 Dashboard 设计原则

```
一屏看懂产品健康度：
  ├── 北极星指标（今日 vs 昨日 vs 上周同期）
  ├── 用户漏斗（各关键节点转化率）
  ├── 留存曲线（D1 / D7 / D30 趋势）
  ├── 收入指标（MRR / 新增付费 / 流失）
  └── 异常告警（红绿灯状态）
```

指标监控频率

```
实时监控（秒级）：
  └── 崩溃率、支付成功率、核心 API 错误率
      → 任何异常立即告警

小时级监控：
  └── DAU 趋势、核心功能使用量、错误日志
      → 发现业务波动

日级监控：
  └── 留存、激活率、收入指标
      → 追踪趋势变化

周 / 月级监控：
  └── 北极星指标、LTV/CAC、NPS
      → 战略级健康度评估
```

告警阈值设置

```
静态阈值：绝对值超过预设上下限触发告警
  适用：崩溃率 > 1%、支付失败率 > 5%

动态阈值：相比历史基线异常偏离触发告警
  适用：DAU 环比下降 > 15%、转化率突变

复合告警：多个指标同时异常才触发
  适用：减少噪音，聚焦真实问题
```

### 产品层监控

功能健康度监控

```
每个核心功能需要追踪：
  使用渗透率    → 有多少用户在用这个功能
  使用频次      → 使用的用户用得有多频繁
  完成率        → 开始使用后是否顺利完成
  错误率        → 功能调用的失败比例
  用户满意度    → 点赞 / 点踩 / 评分反馈
```

用户反馈监控

```
结构化反馈：
  ├── NPS 调研（季度）
  ├── CSAT（功能使用后即时评分）
  └── 产品内反馈入口（随时收集）

非结构化反馈：
  ├── 应用商店评论（AppFollow 监控）
  ├── 社交媒体舆情（关键词监听）
  ├── 客服工单分类（高频问题聚类）
  └── 用户社群讨论（运营人工巡检）
```

反馈闭环机制

```
用户反馈
    ↓
分类 & 优先级标记（自动 + 人工）
    ↓
进入需求池评估
    ↓
立项或排期
    ↓
修复 / 上线
    ↓
通知反馈用户（关闭循环）← 大多数产品缺少这步
```

### 性能层监控

核心性能指标（前端，Core Web Vitals）

> ⚠️ 指标更新：FID（First Input Delay）已被 Google 于 2024 年 3 月正式替换为 INP（Interaction to Next Paint），作为 Core Web Vitals 的交互响应指标。请勿继续使用 FID。参考：web.dev/articles/inp

```
FCP（First Contentful Paint）  → 用户看到内容的时间 < 1.8s
LCP（Largest Contentful Paint）→ 主要内容加载完成 < 2.5s
INP（Interaction to Next Paint）→ 交互响应时间 < 200ms（良好）
                                      < 500ms（需改进）
CLS（Cumulative Layout Shift） → 页面稳定性 < 0.1
TTI（Time to Interactive）     → 页面可交互时间 < 3.8s
```

> 阈值说明：上述数字为 Google 推荐的通用基线。实际产品应按真实用户数据（RUM）、设备分布（高端机 vs 低端机）、业务路径（关键转化路径要求更严）设定自己的阈值，而非把通用标准当作教条。

核心性能指标（后端）

```
API 响应时间（P50 / P95 / P99）
  P50 < 200ms / P95 < 500ms / P99 < 1s

可用性（Availability）
  目标：99.9%（每月宕机 < 43分钟）
  关键路径：99.99%（每月宕机 < 4分钟）

错误率（Error Rate）
  5xx 错误率 < 0.1%
  业务错误率按场景设阈值
```

## 2️⃣ 问题诊断与根因分析

目标：快速、准确地找到问题根源，而非反复救火

### 问题分类体系

```
P0 紧急事故（立即响应）
  └── 核心功能不可用、数据丢失、安全漏洞
  └── 响应时间：15分钟内启动处理

P1 严重问题（当日响应）
  └── 核心指标异常下跌、高频 Bug
  └── 响应时间：2小时内开始排查

P2 一般问题（本周响应）
  └── 次要功能异常、体验问题
  └── 响应时间：进入本周排期

P3 优化建议（排期跟踪）
  └── 体验优化、非紧急改进
  └── 响应时间：进入 Backlog 评估
```

### 根因分析方法论

数据异常排查五步法

```
Step 1：确认异常真实性
  └── 是数据采集问题还是真实业务异常？
  └── 检查埋点、口径、数据管道

Step 2：定位异常范围
  └── 什么时间开始？持续多久？
  └── 哪些用户群体受影响？哪些端？哪些功能？

Step 3：关联外部因素
  └── 与版本发布时间对照
  └── 与运营活动时间对照
  └── 与外部事件对照（节假日、竞品动作）

Step 4：下钻分析
  └── 分渠道 / 分设备 / 分用户群 / 分地区
  └── 缩小问题范围，找到最小复现单元

Step 5：形成假设并验证
  └── 提出 1-3 个可能的根因假设
  └── 用数据或复现验证假设
  └── 找到最可能的根因
```

5 Whys 根因追问

```
现象：付费转化率下降 20%
  Why 1：为什么转化率下降？
    → 支付页面跳出率升高
  Why 2：为什么支付页面跳出率升高？
    → 用户在输入信用卡信息时离开
  Why 3：为什么用户在这步离开？
    → 新版本支付表单在移动端显示异常
  Why 4：为什么表单显示异常？
    → 上周更新了表单组件，未做移动端测试
  Why 5：为什么没做移动端测试？
    → 验收流程没有强制要求移动端回归
  
根因：验收流程缺少移动端测试卡口
改进：将移动端验收加入上线 Checklist
```

鱼骨图分析（复杂问题）

```
                    问题现象
                       │
    ┌──────────────────┼──────────────────┐
    │                  │                  │
  产品侧             技术侧             外部因素
    │                  │                  │
  功能缺陷           性能问题           竞品动作
  体验问题           Bug               市场变化
  引导不清           数据异常          用户预期变化
```

### 事故复盘（Postmortem）

事故复盘文档结构

```
1. 事故摘要
   发生时间、持续时长、影响范围、严重程度

2. 事故时间线
   每个关键节点：发现 / 升级 / 响应 / 缓解 / 解决

3. 根因分析
   直接原因 + 深层根因（用 5 Whys 追溯）

4. 影响评估
   受影响用户数、业务损失、数据影响

5. 修复措施
   已完成的临时修复
   待完成的永久修复（含负责人 + 截止日期）

6. 预防措施
   如何避免同类问题再次发生
   流程 / 监控 / 测试的改进项
```

> ​事故复盘的目的是「系统改进」，不是「追责个人」​——没有改进项落地的复盘是无效的

## 3️⃣ 迭代决策框架

目标：建立科学的迭代节奏，让每次迭代都有清晰的学习目标

### 迭代规划框架

双钻石迭代模型

```
       发散                 收敛
问题空间：              解决方案空间：
探索用户问题      →     定义正确问题
收集数据反馈            设计解决方案
                              ↓
                        发散              收敛
                    方案探索：          方案落地：
                    创意发想      →     选定方案
                    原型验证            开发上线
```

迭代节奏设计

```
快速迭代（1-2周 Sprint）
  └── 适用：功能优化、Bug 修复、小实验
  └── 特点：快速假设-验证循环

中型迭代（4-6周）
  └── 适用：新功能开发、体验重设计
  └── 特点：有足够时间做用户研究和验证

大型迭代（季度级）
  └── 适用：战略方向调整、大版本重构
  └── 特点：需要充分的前期探索和风险评估
```

### 迭代优先级决策

需求决策四象限

```
            高用户价值
                │
  快速执行      │  战略投资
  （低成本高价值）│  （高成本高价值）
────────────────┼────────────────
  暂缓或放弃    │  重新评估
  （低成本低价值）│  （高成本低价值）
                │
            低用户价值
      低执行成本        高执行成本
```

Stop Doing List（同样重要）

```
每个迭代周期需要决策：
  ├── 哪些功能可以下线（降低维护成本）
  ├── 哪些实验结果为负 → 回滚
  ├── 哪些运营活动 ROI 不达标 → 停止
  └── 哪些流程可以简化 → 减少团队负担
```

> 产品的成熟度不只体现在加了什么，也体现在果断放弃了什么

### 数据与直觉的平衡

```
纯数据驱动的陷阱：
  └── 数据告诉你「发生了什么」，不告诉你「应该怎么做」
  └── 局部最优（A/B 测试优化按钮颜色）vs 全局最优（重新设计流程）
  └── 数据不能发现用户「尚未表达的需求」

纯直觉驱动的陷阱：
  └── HiPPO 效应（最高薪人员的意见主导决策）
  └── 确认偏误（只看支持自己想法的数据）
  └── 幸存者偏误（只听活跃用户的声音）

平衡原则：
  用数据验证方向，用直觉识别机会
  用数据否定假设，用直觉提出假设
  小决策数据驱动，大决策数据参考
```

### 迭代学习记录

产品决策日志（Decision Log）

```
每个重要决策记录：
  决策时间：
  决策内容：我们决定做 / 不做 XX
  决策依据：数据 / 用户反馈 / 战略判断
  预期结果：我们预期会发生什么
  实际结果：（事后填写）发生了什么
  学到了什么：下次类似决策的参考

价值：
  → 避免重复踩同一个坑
  → 新成员快速理解产品历史
  → 积累产品判断力的组织记忆
```

## 4️⃣ 产品健康度管理

目标：从整体视角评估产品是否在正确的轨道上，而非陷入局部指标优化

### 产品健康度评估框架

HEART 框架（Google）

```
Happiness    幸福感  → NPS、CSAT、应用评分
Engagement   参与度  → 使用频次、会话时长、功能深度
Adoption     采用率  → 新功能渗透率、新用户激活率
Retention    留存率  → D1 / D7 / D30 留存
Task Success 任务成功率 → 核心任务完成率、错误率
```

产品生命周期诊断

```
导入期（0-1）
  健康信号：找到 PMF、早期用户高度认可
  警示信号：留存曲线持续下滑、用户使用场景分散

成长期（1-10）
  健康信号：有机增长 > 付费增长、NRR > 100%
  警示信号：CAC 持续升高、增长高度依赖营销投入

成熟期（10-稳定）
  健康信号：高留存、强网络效应、品牌护城河
  警示信号：增长停滞、用户老龄化、创新乏力

衰退期
  健康信号：积极转型、探索第二曲线
  警示信号：核心指标全面下滑、用户迁移至竞品
```

### PMF（产品市场契合度）持续检验

Sean Ellis 测试

```
问题：「如果这个产品明天消失，你会有什么感受？」

选项：
  A. 非常失望
  B. 有点失望
  C. 无所谓
  D. 乐于见到（产品对我没用）

PMF 判断标准：
  选 A「非常失望」的用户 > 40% → 达到 PMF
  20-40% → 接近 PMF，继续优化
  < 20%  → 尚未找到 PMF，需要重新审视
```

PMF 信号清单

```
定性信号（用户在说什么）：
  ├── 用户主动向他人推荐
  ├── 用户投诉你不够用，而非不好用
  ├── 用户愿意忍受产品缺陷继续使用
  └── 媒体和社区自发讨论

定量信号（数据在说什么）：
  ├── D30 留存 > 行业基准
  ├── 有机增长占比 > 50%
  ├── NPS > 40
  └── LTV / CAC > 3
```

### 第二曲线探索

何时开始探索第二曲线

```
成熟期主曲线增长放缓时
    ↓
主曲线仍在顶峰时开始探索（而非衰退时）
    ↓
用主曲线的利润和资源孵化新曲线
    ↓
新曲线成长为下一条主曲线
```

第二曲线识别框架

```
用户维度：现有用户的未满足需求
          全新用户群体的未解决问题

技术维度：现有技术能力的新应用场景
          新技术带来的新可能性（如 AI）

市场维度：相邻市场的扩张机会
          现有定位的垂直深化
```

### 产品退场（Sunset）

> 产品生命周期终点同样需要方法论。仓促下线会伤害用户信任、引发舆情、留下合规尾巴——退场和上线一样需要规划。

退场决策判断

```
何时应该退场：
  ├── 持续 N 个季度未达 PMF 复检标准（参考 Sean Ellis 测试 < 20%）
  ├── 单位经济模型长期无法转正（LTV/CAC < 1 持续）
  ├── 维护成本超过战略价值，且无第二曲线可能
  ├── 上游依赖失效（平台政策、技术栈淘汰、监管禁止）
  └── 机会成本：团队投入其他产品价值显著更高

何时不要急于退场：
  ├── 处于衰退期但有可转型的第二曲线机会
  ├── 仍有高价值核心用户群（即使规模小）
  └── 退场会破坏生态承诺（如 API、集成、数据托管）
```

退场执行清单

```
1. 决策与公告
   ├── 明确退场时间表（公告日 → 停止新用户日 → 停止服务日）
   ├── 公告渠道：应用内通知、邮件、官网、应用商店
   └── 说明退场原因和后续安排，避免用户恐慌

2. 用户过渡
   ├── 提供数据导出工具（标准格式，至少留 30 天窗口）
   ├── 推荐替代方案（竞品或自家其他产品）
   ├── 付费用户退款机制（按剩余时长折算）
   └── 高价值用户 1:1 沟通（企业客户、KOL）

3. 数据处理
   ├── 明确数据保留与删除策略（符合隐私法规）
   ├── 用户数据删除承诺与执行日志
   └── 法律要求保留的数据按规归档

4. 生态衔接
   ├── 通知依赖本产品的第三方（API、集成、插件）
   ├── 给出迁移期，避免生态断链
   └── 文档归档，保留可查的知识资产

5. 团队与资产
   ├── 复盘退场原因（沉淀到决策日志）
   ├── 团队成员重新分配
   └── 可复用的技术资产、用户洞察归档入库
```

退场后复盘

```
关键问题：
  ├── 退场决策是否及时？是否拖得太久或太仓促？
  ├── 用户过渡是否平稳？有无重大投诉或舆情？
  ├── 沉淀了哪些可复用的资产（用户群、技术、洞察）？
  └── 这次退场对组织学习到什么？下次如何更早识别不可持续的产品？
```

## 方法论闭环：监控如何驱动下一轮迭代

```
产品监控（发现信号）
        ↓
问题诊断（理解信号）
        ↓
回到「产品探索与发现」（深度理解用户）
        ↓
或回到「产品构思与设计」（设计解决方案）
        ↓
或回到「产品度量与数据」（重新定义指标）
        ↓
迭代上线 → 继续监控
        ↓
        ∞（持续循环）
```

## 阶段卡口（决策门 — 整个方法论的闭环检验）

> 📌 按决策门规范执行，详见 [[产品方法论总览#阶段卡口 → 决策门规范]]。本卡口是整个方法论的闭环检验，等级：**A 级**。监控的产出必须回流到 [[10 决策内核]] 的假设重评。

这是循环三的终点，也是回流到循环一/二的起点。需要回答：

1. ✅ 有清晰的监控体系，核心指标异常能在 15 分钟内发现？（A 级，L2 证据：监控 Dashboard + 告警规则）
2. ✅ 有规范的根因分析流程，事故不会重复发生？（A 级，L2 证据：事故复盘记录 + 改进项跟踪）
3. ✅ 迭代决策有数据支撑，不是靠拍脑袋排优先级？（A 级，L2 证据：优先级矩阵 + 数据依据）
4. ✅ 定期做 PMF 检验，知道产品是否仍然契合市场？（A 级，L3 证据：PMF 量化指标 + 趋势分析）
5. ✅ 监控发现的问题能流回探索阶段，形成真正的闭环？（A 级，L2 证据：回流案例 + OST 更新记录）
6. ✅ **监控信号已触发 [[10 决策内核]] 假设台账的重评？**（A 级，L1 证据：假设状态更新记录）

回流触发条件（关键）：

```
监控信号触发回流到循环一（意图与探索）：
  ├── PMF 指标持续下滑 → 重新探索用户价值
  ├── 出现新的竞争格局 → 重新评估战略边界
  └── 用户结构发生重大变化 → 重新定义目标用户

监控信号触发回流到循环二（方案与验证）：
  ├── 核心功能使用率低于预期 → 重新设计方案
  ├── 度量契约的成功标准未达成 → 重新验证假设
  └── 出现新的用户行为模式 → 新增机会到 OST
```
