# 产品方法论总览

这是一套个人产品方法合集，用来组织产品从机会发现到增长迭代的完整链路。

它放在常青笔记的方法区，但不是单篇原子化常青笔记，而是一个"方法合集入口"。其中可以复用的独立观点，后续再继续拆成更小的常青笔记。

---

## 产品哲学与决策原则（草稿）

> ⚠️ 本节为草稿，待用户确认。哲学是个人化的，以下原则基于已有笔记和偏好推断，请按真实想法增删改。

当工具之间冲突时（体验 vs 商业、数据 vs 直觉、速度 vs 质量），方法论需要顶层裁决原则。

```
原则 1：用户价值优先于商业指标
  ├── 没有用户价值的商业模型不可持续
  ├── 虚荣指标不等于用户价值
  └── 商业化是用户价值的变现，不是收割

原则 2：可逆决策快速试错，不可逆决策充分论证
  ├── Type 2（可逆）：70% 信息即可决策，用实验验证
  ├── Type 1（不可逆）：必须充分论证，宁可慢
  └── 多数 PM 的错误是把可逆决策当不可逆决策拖延

原则 3：先发散再收敛，禁止过早锁死方案
  ├── 第一个想法通常不是最优解
  ├── 重大方向决策前必须有至少 3 个候选方案
  └── 收敛基于明确标准，而非"感觉"

原则 4：用数据减少猜测，但不让数据替代判断
  ├── 数据告诉你"发生了什么"，不告诉你"该怎么办"
  ├── 小决策数据驱动，大决策数据参考
  └── 警惕 HiPPO（最高薪者意见）和确认偏误

原则 5：做减法比做加法更难，也更重要
  ├── 拒绝服务所有人，聚焦核心用户
  ├── Stop Doing List 与 To Do List 同等重要
  └── 产品的成熟度也体现在果断放弃了什么

原则 6：探索与交付双轨并行，而非线性阶段
  ├── 探索（Discovery）和交付（Delivery）同时进行，互不阻塞
  ├── 不要"做完探索再做交付"——那是伪敏捷的瀑布流
  ├── 每周持续接触用户，持续更新机会方案树（OST）
  └── 详见 [[02 产品探索与发现#机会方案树（OST）—— 从探索到构思的桥梁]]
```

## 主链路：非线性三循环模型

> ⚠️ 关键升级：原"七站式流水线"已重构为**三循环 + 双横切层**模型。原因：产品工作不是线性阶段交付，探索与商业、构思与度量、交付与增长都是双向耦合的。线性模型会导致"研究完再定战略""设计完再想怎么量"的伪流程。

### 三循环结构

```
┌─────────────────────────────────────────────────┐
│ 循环一：意图与探索循环（双向耦合）                  │
│                                                   │
│   产品意图与约束  ←→  探索发现                     │
│   （01 商业战略）    （02 用户研究 + OST）          │
│                                                   │
│   说明：                                           │
│   • 商业战略提供目标用户、资源、风险边界             │
│   • 探索提供用户证据，回流修正战略                   │
│   • 两者是双向耦合，不是先后顺序                     │
└─────────────────────────────────────────────────┘
                    ↓
┌─────────────────────────────────────────────────┐
│ 循环二：方案与验证循环（双向耦合）                  │
│                                                   │
│   机会 / 方案 / 实验  ←→  度量与评估契约            │
│   （03 构思设计 + OST）  （04 度量横切层）          │
│                                                   │
│   说明：                                           │
│   • 方案定义时同步建立"如何判断对错"的度量契约       │
│   • 度量不是事后环节，而是方案设计的一部分           │
│   • PRD 与埋点设计、Evals、实验设计同步产出         │
└─────────────────────────────────────────────────┘
                    ↓
┌─────────────────────────────────────────────────┐
│ 循环三：交付与增长循环（含 GTM 与监控回流）          │
│                                                   │
│   交付 / 发布 / GTM  →  增长与监控  ────┐         │
│   （05 开发上线 + GTM）（06 增长 + 07 监控）│         │
│                                          │         │
│   说明：                                  ↓         │
│   • GTM 是交付到增长的必备环节               │         │
│   • 监控发现信号后回流到循环一/二            │         │
│   • 形成持续探索的闭环                       │         │
└─────────────────────────────────────────────────────┘
                    ↑ 回流（持续探索）
                    │
              重回循环一或二
```

### 各循环的入口与出口

```
循环一（意图与探索）
  入口：新产品立项 / 第二曲线探索 / 重大转型
  出口：明确的用户机会 + 战略边界 + 北极星指标
  关键产物：产品论点、假设台账、机会方案树

循环二（方案与验证）
  入口：明确的用户机会
  出口：经过验证的方案 + 度量契约 + 实验结果
  关键产物：PRD + 埋点设计 + Evals + A/B 实验报告

循环三（交付与增长）
  入口：经过验证的方案
  出口：上线 + GTM 完成 + 增长数据 + 监控信号
  关键产物：发布版本 + GTM 资产 + 增长飞轮 + 监控 Dashboard
```

### 与原编号的映射

原文件编号保留（避免破坏双链），但实际工作流程按三循环推进：

```
循环一：01 商业战略 + 02 探索发现（双向耦合）
循环二：03 构思设计 + 04 度量数据（双向耦合）
循环三：05 开发上线（含 GTM）+ 06 增长运营 + 07 监控迭代
```

## 情境路由与适配指南

> 本方法论默认面向"中等规模团队 + 已有产品 + 迭代优化"情境。不同情境需裁剪。

### 按产品阶段路由

```
0→1（PMF 探索期）：
  ├── 重点模块：02 探索、03 构思（MVP）、07 PMF 检验
  ├── 轻量模块：01 商业（粗框架即可）、04 度量（定性强于定量）
  ├── 可跳过：05 重型发布流程、06 规模化增长
  └── 核心动作：Do Things That Don't Scale，做不可扩展的事

1→10（规模化增长期）：
  ├── 重点模块：04 度量、06 增长、05 开发
  ├── 强化模块：01 商业（单位经济模型）、08 执行节奏
  └── 核心动作：找到可规模化的获客渠道，建立增长飞轮

10→稳定（成熟期）：
  ├── 重点模块：07 监控迭代、第二曲线探索
  ├── 强化模块：01 战略路线图、08 跨职能协作
  └── 核心动作：防守主曲线，用利润孵化第二曲线
```

### 按团队规模路由

```
独立开发者 / 1-3 人小团队：
  ├── 大幅精简：08 项目管理（无需重型流程，保留节奏感即可）
  ├── 重点保留：02 探索、03 构思、04 度量
  └── 工具轻量化：避免 Jira / Confluence 等重型工具

中等规模团队（10-50 人）：
  ├── 方法论默认配置，全面适用
  └── 重点强化：08 跨职能协作界面

大型组织 / 多产品线：
  ├── 额外需要：产品组合管理、资源分配机制、多产品路线图协同
  └── 本方法论聚焦单产品，多产品管理需另立方法
```

### 按 AI 含量路由

```
传统软件产品：
  ├── 主链路 01-07 完全适用
  └── 09 AI 模块可跳过

AI 增强产品（AI 作为功能点）：
  ├── 主链路 01-07 仍然适用
  ├── 09 AI 模块选择性参考（重点是 §2 Evals、§3 UX）
  └── 成本结构需局部调整

AI 原生产品（AI 是核心价值）：
  ├── 主链路 01-07 需配合 09 重构
  ├── 09 为必读，尤其是 §2 Evals、§4 双轨迭代、§5 成本、§6 安全
  └── 经典方法如 Kano、AARRR 仍适用，但需叠加 Evals 维度
```

### 阶段卡口 → 决策门规范

> ⚠️ 关键升级：原"硬/软卡口"是分类标签，难以执行。已重构为**决策门**——每个卡口都是一次明确的决策，需回答"证据-责任人-风险-复核"四要素。所有模块的卡口按此规范执行。

#### 决策门四要素

```
每个卡口进入下一阶段时，必须明确：

要素 1：证据（Evidence）
  ├── 需要什么级别的证据才能放行？
  │     ├── L1 弱证据：推理、个别访谈（样本<5人）、专家主观判断
  │     ├── L2 中等证据：小规模实验（样本<100）、原型测试通过、技术 PoC 跑通
  │     ├── L3 强证据：A/B 实验（统计显著 p<0.05）、上线灰度数据、法务/安全正式邮件签批
  │     └── L4 共识证据：大规模放量数据（如财报级）、高管会正式决议
  └── 不同卡口要求不同的最低证据级别

要素 2：责任人（Owner）
  ├── 谁有放行权？（明确到个人，不是"团队")
  ├── 谁是风险接受人？（带风险放行时必须签字）
  └── 谁负责复核？（与放行人可以是不同角色）

要素 3：风险（Risk）
  ├── 带风险放行的具体风险是什么？
  ├── 风险等级（低/中/高）？
  ├── 补偿措施是什么？（灰度、告警、回滚、限时）
  └── 风险接受人是否签字？

要素 4：复核（Review）
  ├── 何时复核？（具体日期或触发条件）
  ├── 复核标准是什么？（什么结果算通过/打回）
  ├── 自动失效条件是什么？（超时未复核、关键指标未达）
  └── 出问题的回滚条件是什么？
```

#### 卡口等级与放行规则

```
S 级卡口（红线，不可降级）：
  ├── 用户问题真实性（02）：没有真实问题，不进入方案设计
  ├── 安全合规底线（05/09）：监管红线不可绕过
  └── P0 Bug 清零（05）：核心功能不可用不能上线
  → 必须达到 L3 以上证据，由产品负责人 + 风险接受人双签

A 级卡口（默认不放行，可条件性放行）：
  ├── 商业模式清晰度（01）
  ├── 技术可行性验证（05）
  ├── GTM 准备就绪（05）
  └── AI 安全边界（09）
  → 默认要求 L2 以上证据；带风险放行需：
     ├── 风险接受人签字
     ├── 明确补偿措施（灰度/告警/回滚）
     └── 设定复核日期（通常 2-4 周内）

B 级卡口（启发式，建议但不强制）：
  ├── 路线图对齐度（01）
  ├── 指标体系完整度（04）
  └── 文档完整度（03）
  → 可由 PM 自主判断，记录决策即可
  → 适用于 0→1 阶段或小团队，规模化后应升级为 A 级
```

#### 决策门记录格式

```
每次卡口放行必须记录（接入 [[10 决策内核]] 的决策记录）：

卡口名称：______________________
卡口等级：S / A / B
放行决策：放行 / 带风险放行 / 不放行

证据：
  ├── 证据级别：L1 / L2 / L3 / L4
  └── 证据来源：______________________

责任人：
  ├── 放行决策人：______________________
  ├── 风险接受人：______________________（带风险放行时必填）
  └── 复核负责人：______________________

风险（带风险放行时必填）：
  ├── 风险描述：______________________
  ├── 风险等级：低 / 中 / 高
  └── 补偿措施：______________________

复核：
  ├── 复核日期：______________________
  ├── 复核标准：______________________
  ├── 自动失效条件：______________________
  └── 回滚条件：______________________
```

> 关键转变：卡口从"checklist 打勾"升级为"决策留档"。每次放行都是一次明确的决策，可追溯、可复盘、可学习。这与 [[10 决策内核]] 的决策记录对象完全打通。

## 方法论自我复盘（元机制）

> 这套方法论本身需要迭代。每隔一段时间回答以下问题，判断方法论是否仍有效。

```
复盘周期：每季度一次，或在重大产品节点后

核心问题：
  1. 这套方法是否帮助我做出了更好的决策？
     ├── 如果没有，是方法本身的问题，还是我用错了？
     └── 哪些决策是方法论指导的？哪些是直觉的？结果差异如何？

  2. 哪些模块在实践中从未用到？
     ├── 是模块不适用，还是我遗漏了？
     ├── 长期不用的模块考虑删除或降级为附录

  3. 哪些实践中的方法没有沉淀进方法论？
     ├── 我反复用的方法但方法论里没有 → 应该补进来
     ├── 这次产品踩的坑 → 是否需要新增方法或卡口

  4. 方法论是否跟上时代？
     ├── 新技术（如 AI）是否需要新方法？
     ├── 新商业模式是否需要新框架？
     └── 工具栈是否需要更新？

  5. 方法论是否仍契合我的真实工作情境？
     ├── 情境变化（团队规模、产品阶段）后是否需要裁剪？
     └── 是否需要新增情境路由分支？
```

> 方法论是工具，不是教条。当方法论与实践冲突时，先信实践，再改方法论。
