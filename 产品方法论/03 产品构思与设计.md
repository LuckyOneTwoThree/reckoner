# 方法论展开

这个模块的核心命题是：​「把正确的问题，转化为正确的解决方案」​。是 PM 最高频的日常战场。

---

## 模块结构总览

```
产品构思与设计
├── 1. 需求管理
├── 2. 创意发散与方案构思
├── 3. 产品设计与原型
└── 4. 方案验证
```

---

## 1️⃣ 需求管理

目标：建立需求的收集、筛选、流转机制，而非需求的无限堆积

### 需求来源全景

```
需求池
├── 用户侧：访谈、反馈、客诉、NPS 评论
├── 业务侧：销售、客服、运营一线
├── 数据侧：行为异常、漏斗断点、搜索词
├── 竞品侧：功能对标、市场动态
└── 战略侧：OKR 拆解、高层意图
```

> ⚠️ 最危险的需求来源：「老板说要做」「竞品有我们没有」——需要还原背后真实问题

### 需求四步处理流程

```
收集 → 理解 → 评估 → 决策
```

​收集​：统一入口（需求池），避免口头需求直接进排期

​理解​：需求拆解模板

```
用户是谁？
他们在什么场景下？
遇到了什么问题？
现在怎么解决的？
理想状态是什么？
```

​评估​：RICE / ICE / 价值 × 成本矩阵（参考上一阶段）

​决策​：明确做 / 不做 / 待定，不做的需求同样需要记录原因

### 需求文档体系

PRD 核心结构

```
1. 背景与目标        ← 为什么做
2. 用户与场景        ← 为谁做
3. 需求描述          ← 做什么
4. 功能设计          ← 怎么做
5. 边界与限制        ← 不做什么
6. 数据埋点          ← 怎么量（埋点设计方法详见 [[04 产品度量与数据#埋点设计规范]]，建议 PRD 阶段同步设计，避免上线后补埋点）
7. 验收标准          ← 做完的定义
```

> PRD 的本质是​决策记录​，不是功能说明书——要讲清楚「为什么这样设计」

## 2️⃣ 创意发散与方案构思

目标：在收敛前充分发散，避免过早锁死方案

### 发散思维工具

How Might We（HMW）启动发散

```
问题陈述：用户在 XX 场景下遭遇 XX 困境
↓
HMW：我们如何帮助用户……？
     我们如何让……变得更容易？
     我们如何消除……的障碍？
```

​SCAMPER 框架​：对现有方案进行创意改造

|字母|含义|问题示例|
|---|---|---|
|S|Substitute 替换|能替换哪个环节？|
|C|Combine 合并|能与什么结合？|
|A|Adapt 调整|能借鉴什么类似方案？|
|M|Modify 修改|放大或缩小某个特性？|
|P|Put to other use 转用|用在其他场景？|
|E|Eliminate 删除|去掉什么会更好？|
|R|Reverse 反转|逆向思考会怎样？|

设计冲刺（Design Sprint）节奏

```
Day 1 理解：对齐问题、用户旅程、专家访谈
Day 2 发散：闪电演示、草图发散（Crazy 8s）
Day 3 决策：方案投票、故事板绘制
Day 4 原型：快速搭建可测试的原型
Day 5 验证：真实用户测试、洞察提炼
```

> 5 天浓缩版适合重大方向决策；日常可只取 Day 2-3 的发散-决策部分

### 方案构思原则

先发散再收敛

```
阶段一（发散）：数量优先，禁止评判
    ↓
阶段二（聚类）：归纳相似方向
    ↓
阶段三（收敛）：基于标准筛选
    ↓
阶段四（深化）：对选定方案细化
```

​思维逆转法​：先想「怎样才能让这个产品完全失败」，再逆向得出成功条件

## 3️⃣ 产品设计与原型

目标：将方案转化为可沟通、可测试的具体形态

### 信息架构设计

IA 核心工作

```
内容清单 → 分类排序 → 层级结构 → 导航模式
```

卡片分类法（Card Sorting）

- 开放式：用户自己决定分类，发现用户心智模型
- 封闭式：用户将内容归入预设分类，验证 IA 假设

​树状测试（Tree Testing）​：验证导航结构是否符合用户预期

### 用户流程设计

Task Flow vs User Flow

```
Task Flow：单一任务的操作步骤（线性）
User Flow：包含分支判断的完整路径（有条件节点）
```

用户流程设计核查

- 每一步的目标是否清晰？
- 异常路径是否有处理？
- 最短路径是否足够短？
- 关键决策点是否有充分引导？

### 原型保真度选择

```
低保真（Lo-Fi）         中保真（Mid-Fi）        高保真（Hi-Fi）
纸面草图 / 线框图        灰色线框 + 交互逻辑      接近真实视觉 + 完整交互
↓                       ↓                       ↓
验证流程和结构           验证交互逻辑             验证视觉和细节体验
团队内部对齐             用户测试                 开发交付标准
1小时完成               1天完成                  1周完成
```

> ​原则：用最低保真度回答当前最重要的问题​，不要过早投入高保真

### 设计协作规范

PM 与设计师的边界

```
PM 负责：              设计师负责：
- 用户问题定义          - 交互方案设计
- 功能边界与逻辑        - 视觉与体验细节
- 验收标准              - 设计规范与组件
- 业务优先级            - 可用性专业判断
```

> PM 应该 Review「是否解决了正确的问题」，而非「按钮颜色好不好看」

设计评审 Checklist

- [ ] 是否覆盖核心用户场景？
- [ ] 异常状态是否设计完整（空状态、错误、加载）？
- [ ] 是否与现有设计系统一致？
- [ ] 关键操作路径是否经过可用性验证？

## 4️⃣ 方案验证

目标：在大规模投入前，用最小成本验证核心假设

### 验证思维框架

假设地图

```
我们相信 [用户/场景]
会因为 [功能/改变]
实现 [预期结果]
我们可以通过 [指标] 来验证
最大风险假设是 [XXX]
```

> 每个方案背后都有假设——先识别假设，再设计验证

### 验证方法层级

```
验证成本（低→高）        验证强度（弱→强）
│
├── 专家走查              快速、低成本，发现明显问题
├── 认知走查              模拟用户思维路径
├── 可用性测试            样本量取决于异质性（见下方说明）
├── A/B 测试              数据驱动，需要足够流量
├── 灰度发布              真实环境小范围验证
└── MVP 上线              最真实验证，成本最高
```

> 关于可用性测试样本量：业界常引用的"5 人发现 80% 问题"（Nielsen）是经验法则而非普适结论。实际样本量应考虑：
> - 用户异质性：用户群体越多样，所需样本越多
> - 研究目标：发现明显问题 vs 评估细微体验，后者需要更多样本
> - 新增发现率：每增加一位用户，新发现的问题是否显著减少
> - 连续轮次：跨多轮研究，每轮 3-5 人比一次性 15 人更有效
> 关键不是凑够某个数字，而是观察"新增发现率"是否趋于平缓。

可用性测试核心流程

```
1. 明确测试目标（验证什么假设）
2. 设计任务脚本（真实场景，不引导）
3. 招募目标用户（5-8人）
4. 观察 + 记录（说出想法法）
5. 归纳洞察（问题聚类，严重程度分级）
6. 迭代方案
```

### MVP 设计原则

MVP 的本质是「学习工具」，不是「残缺产品」

MVP 类型选择

| 类型      | 方式       | 适用      |
| ------- | -------- | ------- |
| 落地页测试   | 做页面收集意向  | 验证需求真实性 |
| 人工服务型   | 后台人工替代系统 | 验证服务模式  |
| 向导式 MVP | 最简功能闭环   | 验证核心流程  |
| 单功能 MVP | 只做一个核心功能 | 验证价值主张  |
| 预售型 MVP | 先卖再做     | 验证付费意愿  |

MVP 范围界定

```
必须有（Must Have）：没有它核心价值无法传递
不能有（Must Not）：会干扰用户感知核心价值
可以没有（Nice to have）：留给下一版本
```

## 阶段卡口（决策门）

> 📌 按决策门规范执行，详见 [[产品方法论总览#阶段卡口 → 决策门规范]]。本卡口等级：**A 级**（关键假设必须验证，不可跳过）。注意：04 度量已改为横切层，PRD 必须同步产出埋点与度量契约，不再是"进入 04 后才想"。

进入循环三（交付与增长）之前，需要回答：

1. ✅ 核心需求已有清晰的 PRD，边界明确？（B 级，L1 证据：文档完整即可）
2. ✅ 方案经过发散-收敛，不是第一个想法直接上？（A 级，L2 证据：≥3 候选方案 + 收敛依据）
3. ✅ 关键假设已通过原型或测试初步验证？（A 级，L2 证据：原型测试或 MVP 数据）
4. ✅ MVP 范围已界定，知道哪些是核心，哪些是之后？（B 级，L1 证据：范围说明）
5. ✅ 设计稿已通过 Review，开发可以无歧义理解？（B 级，L1 证据：Review 记录）
6. ✅ **埋点设计与度量契约已与 PRD 同步产出？**（A 级，L2 证据：埋点文档 + 成功标准定义）
7. ✅ **每个 Solution 是否挂载了 [[10 决策内核]] 的假设编号？**（A 级，L1 证据：OST 关联）

带风险放行规则：

```
关键假设未验证不可进入交付（A 级不可降）：
  ├── 必须至少完成 L2 验证（原型测试或小规模实验）
  ├── 带风险放行需风险接受人签字 + 灰度发布 + 告警
  ├── 复核日期：上线后 1-2 周内
  └── 回滚条件：核心假设被证伪
```
