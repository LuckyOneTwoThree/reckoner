# 方法论展开

这个模块的核心命题是：​「AI 原生产品的不确定性，要求方法论的全面重构，而非简单套用经典框架」​。它是横切于 01-07 主链路的方法适配层，不是独立阶段。

> 📌 本模块不是教如何做 AI，而是教如何用产品方法论驾驭 AI 产品。技术细节见 AI 相关概念笔记。

## 1️⃣ AI 产品的本质差异

目标：先承认差异，再谈方法。用经典 PM 方法论硬套 AI 产品，是当前最大的反模式。

### 确定性 vs 概率性

```
传统软件产品              AI 原生产品
─────────────             ─────────────
输入 → 确定性输出          输入 → 概率性输出
功能边界明确              能力边界模糊（涌现的）
断言相等可验收            需评估质量才能验收
Bug 是缺陷                "Bug" 可能是特性或局限
错误可复现                错误难以完全复现
```

> 核心转变：从「设计功能」走向「设计能力 + 设计约束」

### 价值创造路径变化

```
传统产品价值：完成某项功能（工具属性）
AI 产品价值：
  ├── 增强：放大人的判断力（Copilot 范式）
  ├── 生成：创造新内容（生成式范式）
  ├── 自动化：替代人完成流程（Agent 范式）
  └── 个性化：适配个体需求（自适应范式）
```

### 成本结构变化

```
传统产品：开发成本固定，边际成本趋近于零
AI 产品：
  ├── 推理成本：每次调用都有 token / GPU 成本
  ├── 训练 / 微调成本：模型迭代的高额固定投入
  ├── 数据成本：标注、清洗、存储
  └── 成本随使用量线性甚至超线性增长
```

> 这意味着 AI 产品的单位经济模型天然更脆弱，[[06 产品增长与运营#单位经济模型]] 必须把推理成本计入 COGS

## 2️⃣ 评估体系（Evals）—— 扩展传统验收

目标：用「评估质量」扩展「断言相等」，这是 AI 产品与传统产品最大的方法分水岭。

> ⚠️ 定位校正：Evals 是对传统验收的**扩展**而非取代。确定性功能（如按钮点击、表单提交、权限校验）仍需要断言测试、集成测试、安全测试和业务验收。Evals 解决的是"概率性输出无法用断言验收"的部分，两者是叠加关系，不是替代关系。

### Evals 分层架构

```
L1 单元级 Evals（组件）
  └── 单个能力点：如「能否正确提取日期」
  └── 方法：golden set 断言

L2 行为级 Evals（流程）
  └── 端到端任务：如「能否完成一次会议纪要」
  └── 方法：LLM-as-judge + 人工抽检

L3 系统级 Evals（产品）
  └── 整体产品体验：如「用户是否觉得有用」
  └── 方法：A/B 测试、用户满意度、留存

L4 人本评估（价值）
  └── 是否真正解决问题：如「是否节省了用户时间」
  └── 方法：用户访谈、任务完成时间对比
```

### 产品与工程的 Eval 契约

```
Evals 体系必须明确分工，避免产品与研发互相等待：
  ├── PM 职责（定义标准）：
  │     └── 提供基准测试集（Golden Set）的真实业务输入。
  │     └── 用自然语言定义“LLM-as-a-judge”的评判规则（如“是否体现关怀感”）。
  │     └── 详见 [[11 Agent工作流与自动化落地#AI 评估协同 Copilot]]，可通过 Agent 将自然语言自动转化为评测脚本。
  └── 研发职责（工程实现）：
        └── 搭建自动化跑批的评测流水线。
        └── 暴露评测结果看板与底层日志（Trace）。
```

### 评估方法选型

| 方法 | 适用 | 成本 | 陷阱 |
|---|---|---|---|
| Golden Set | 输入输出相对确定的能力 | 低 | 覆盖不全，遗漏长尾 |
| LLM-as-judge | 主观质量评估（如回答质量） | 中 | 评判模型偏见、自评偏差 |
| 人工标注 | 高价值、高风险场景 | 高 | 标注一致性、成本 |
| A/B 对比 | 用户体验维度 | 中 | 需要流量、周期长 |
| Red Team | 安全、边界、失败模式 | 中 | 难以穷举 |

### 评估指标体系

```
质量维度：
  ├── 准确性（Accuracy）：输出是否正确
  ├── 相关性（Relevance）：是否切题
  ├── 完整性（Completeness）：是否覆盖要点
  ├── 一致性（Consistency）：相似输入是否相似输出
  └── 安全性（Safety）：是否有害/越界

工程维度：
  ├── 延迟（Latency）：首 token 时间、完整响应时间
  ├── 成本（Cost）：单次调用 token 消耗
  ├── 可用性（Availability）：模型服务稳定性
  └── 吞吐量（Throughput）：并发处理能力
```

> ⚠️ 经典 [[04 产品度量与数据#指标体系设计]] 仍然适用，但必须叠加 Evals 维度——只看业务指标不看模型质量，等于在沙地上盖楼

### Evals 即产品资产

```
Evals 不是一次性测试，而是持续资产：
  ├── Golden Set 随产品演进扩充
  ├── 失败案例自动沉淀进回归集
  ├── Evals 结果作为模型选型的决策依据
  └── Evals 覆盖率 = 产品的可演进能力上限
```

## 3️⃣ 不确定性下的 UX 设计

目标：让用户在概率性输出中依然感到可控、可信、可用。

### 三种产品形态的 UX 差异

```
Copilot 范式（人主导，AI 辅助）
  ├── 核心：增强人的判断，不替代决策
  ├── UX：可编辑、可拒绝、可追溯
  └── 示例：GitHub Copilot、Notion AI

Workflow 范式（人设定流程，AI 执行步骤）
  ├── 核心：自动化确定性流程，关键节点人介入
  ├── UX：流程可视化、节点可干预
  └── 示例：自动化办公、数据处理 Pipeline

Agent 范式（AI 自主规划与执行）
  ├── 核心：委托目标，AI 自主行动
  ├── UX：行动透明、可中断、可回滚、可审计
  └── 示例：自主任务执行 Agent
```

> Agent 的 UX 设计最复杂，安全边界直接决定部署上限，详见 [[AI Agent 的安全边界决定了它的部署上限]]

### 容错设计原则

> ⚠️ 关键校正：**"所有 AI 操作都应有 undo"不现实**。对于外部系统操作、支付、删除、发信等不可逆动作，无法靠 undo 解决，必须采用预览、权限隔离、人工确认、补偿操作与审计的组合策略。

```
按操作可逆性分级设计：

可逆操作（产品内部状态）：
  ├── 默认可撤销，提供 undo 路径
  ├── 撤销有时间窗口（如 5 分钟内）
  └── 撤销日志可追溯

不可逆但可补偿（外部系统、资金、消息）：
  ├── 预览：执行前展示完整影响（dry-run）
  ├── 权限隔离：AI 不能直接执行，需人工授权
  ├── 人工确认：关键节点必须由人点击"确认执行"
  ├── 补偿操作：出错时启动补偿流程（如退款、撤回消息）
  └── 审计日志：完整记录 AI 提议、人确认、执行结果

完全不可逆（删除、永久操作）：
  ├── AI 仅能提议，不能执行
  ├── 必须人工二次确认 + 延时执行（如 24h 冷静期）
  └── 操作前强制备份 / 快照
```

渐进式信任：

```
  ├── 低风险操作自动执行
  ├── 中风险操作需确认
  ├── 高风险操作需人工审核
  └── 信任等级随使用历史动态调整
```

优雅失败：

```
  ├── AI 失败时降级到规则 / 模板 / 人工
  ├── 明确告知用户失败，而非掩盖
  └── 失败也是学习信号，回流到 Evals
```

### 透明度设计

> ⚠️ 关键校正：**避免承诺"展示推理过程"**。大模型的 chain-of-thought 不等同于真实推理，展示可能误导用户信任。更稳妥的是展示可验证的事实依据。

```
让用户理解 AI 的能力边界：
  ├── 展示来源（数据源、引用文献、原始文档片段）
  ├── 展示依据（关键证据、支撑事实）
  ├── 展示工具调用（调用了哪些 API、检索了哪些数据）
  ├── 展示行动日志（Agent 产品的操作序列）
  ├── 展示局限性（什么做不好、什么没把握）
  └── 避免展示"推理过程"——可能造成虚假信任
  └── 避免过度拟人化，造成错误信任

延迟与体验：
  ├── 流式输出降低感知延迟
  ├── 长任务提供进度反馈
  ├── 可中断、可续传
  └── 设定响应时间上限，超时降级
```

## 4️⃣ 双轨迭代：模型迭代 vs 产品迭代

目标：理解 AI 产品的迭代有两条轨道，需要解耦管理。

### 双轨模型

```
模型迭代轨道（慢周期：周-月）
  ├── 模型版本升级（自研 / 第三方）
  ├── Prompt / 系统提示词优化
  ├── 微调（SFT / RLHF）
  ├── RAG 知识库更新
  └── 工具与函数定义更新

产品迭代轨道（快周期：天-周）
  ├── 交互流程优化
  ├── 功能边界调整
  ├── UX 细节打磨
  ├── 新场景接入
  └── 触达与运营策略
```

### 模型升级的回归风险

```
模型升级 ≠ 能力单调提升
  ├── 能力漂移：原来能做的现在做不好
  ├── 行为变化：输出风格、格式变化
  ├── 成本变化：新版本可能更贵或更慢
  └── 安全新风险：原来被拒绝的现在可能放行

应对：
  ├── 每次模型升级必须跑全量 Evals 回归
  ├── 灰度发布 + 实时质量监控
  ├── 保留旧版本作为 fallback
  └── Prompt 版本与模型版本绑定管理
```

### Prompt 工程的产品化

```
Prompt 不是临时脚本，而是产品资产：
  ├── 版本管理：与代码同等对待
  ├── A/B 测试：不同 Prompt 的效果对比
  ├── 环境隔离：dev / staging / prod 的 Prompt 分离
  ├── 回滚能力：Prompt 出问题可秒级回退
  └── 评审机制：Prompt 变更需 Review
```

### 数据飞轮设计

> ⚠️ 关键校正：**失败案例不应默认进入微调**。直接把失败案例塞进训练集是常见反模式，会导致模型"记住"错误而非"理解"正确。必须先做根因分流，对症下药。
> 💡 建议接入“AI 评估协同 Copilot”工作流（见 [[11 Agent工作流与自动化落地]]），由 Agent 抓取底层复杂的调用 Trace，并“翻译”成产品视角的 Bad Case 报告（如：反馈失败是因为“检索未命中知识库文档X”），填补产品与工程的认知鸿沟。

```
用户使用数据反哺产品：
  ├── 显式反馈：点赞 / 点踩、修改、采纳
  ├── 隐式反馈：是否复制、是否编辑、是否分享
  ├── 失败案例：自动收集低分输出，先分流再处理
  └── 场景发现：用户用法的长尾分布指导产品扩展
```

失败案例的根因分流（必做）：

```
收集到失败案例后，先判断属于哪类问题：

├── 知识问题（事实错误、信息缺失）
│     └── 处理：补充 RAG 知识库 / 更新数据源
│     └── 不进训练集
│
├── 检索问题（相关知识没被召回）
│     └── 处理：优化检索策略 / Embedding / Reranker
│     └── 不进训练集
│
├── 工具问题（API 调用失败、参数错误）
│     └── 处理：修复工具定义 / 增强工具描述
│     └── 不进训练集
│
├── Prompt / 策略问题（指令理解偏差、流程错误）
│     └── 处理：优化系统 Prompt / 调整 Agent 编排
│     └── 不进训练集
│
├── UX 问题（用户预期与产品呈现不匹配）
│     └── 处理：改进交互设计 / 期望管理
│     └── 不进训练集
│
└── 模型能力问题（确实是模型不会做）
      └── 处理：进入微调候选集
      └── 但仍需评估：是否值得微调？数据是否足够？
      └── 考虑替代方案：换更大模型 / 用工具补足
```

> 关键洞察：多数"AI 表现不好"的问题根源不在模型能力，而在知识、检索、工具、Prompt 或 UX。盲目微调不仅浪费资源，还可能引入新问题。先分流，再决定处理路径。

数据飞轮的伦理边界：

```
  ├── 用户知情同意
  ├── 敏感数据脱敏
  ├── 不滥用用户内容训练（除非明确授权）
  └── 遵守数据保留与删除法规
```

## 5️⃣ 成本结构与商业模式适配

目标：把推理成本纳入产品方法论的核心变量，而非事后考虑。

### 成本结构分析

```
单次调用成本分解：
  ├── 输入 token 成本
  ├── 输出 token 成本
  ├── 工具调用成本（搜索、API）
  ├── RAG 检索成本
  └── 存储 / 上下文成本

成本控制杠杆（按收益排序）：
  ├── 模型选型：简单任务用小模型，复杂任务才上大模型
  ├── 缓存：相同输入缓存结果，避免重复推理
  ├── 路由：根据任务复杂度动态路由到不同模型
  ├── 批处理：非实时任务用 batch API 降本
  ├── 上下文压缩：精简 prompt，去除冗余
  ├── 蒸馏 / 微调：将大模型能力蒸馏到小模型
  └── 提前终止：达到阈值即停止生成
```

### 定价模式选择

| 定价模式 | 适用 | 风险 |
|---|---|---|
| 按 token 计费 | API 类产品、开发者用户 | 用户难以预估成本 |
| 订阅制 | 通用 SaaS、消费级 | 重度用户亏损 |
| 用量分层 | 中度复杂场景 | 阶梯设计复杂 |
| 价值定价 | 高价值 B 端场景 | 价值难以量化 |
| 广告变现 | C 端免费产品 | 推理成本与广告收入倒挂 |

### 单位经济模型重构

```
经典 LTV/CAC 模型需要扩展：
  传统：LTV / CAC > 3
  AI 产品：
    LTV（净） = 用户收入 - 用户推理成本 - 用户服务成本
    LTV / CAC > 3 仍成立，但必须用净 LTV

关键监控：
  ├── 单用户推理成本趋势（应随优化下降）
  ├── 毛利率（扣除推理成本后）
  ├── 重度用户占比与成本占比（80/20 失衡风险）
  └── 免费用户的成本上限（防止白嫖拖垮）
```

## 6️⃣ 安全边界与合规

目标：AI 产品的风险面远大于传统产品，安全设计必须前置，不能后补。

### 风险分类

```
内容风险：
  ├── 生成有害 / 违规内容
  ├── 幻觉（Hallucination）导致错误信息
  ├── 偏见与歧视
  └── 版权侵权（生成内容 / 训练数据）

行为风险（Agent 产品）：
  ├── 越权操作
  ├── 不可逆操作未授权
  ├── 数据外泄
  └── 被注入攻击（Prompt Injection）

系统风险：
  ├── 模型服务中断
  ├── 数据泄露
  └── 成本失控（如被恶意调用）

合规风险：
  ├── 生成式 AI 备案（中国）
  ├── 算法登记与披露
  ├── 训练数据合规
  ├── 未成年人保护
  └── 个人信息保护
```

### 安全设计原则

```
最小权限：Agent 只能访问完成任务所需的最小资源
默认安全：高风险操作默认关闭，需显式开启
可审计：所有 AI 决策与行动有日志可追溯
可中断：用户可随时停止 AI 的执行
可回滚：AI 的操作按可逆性分级处理（详见本模块 §3 容错设计原则）
```

### 红队测试

```
主动发现失败模式：
  ├── 对抗性输入测试（Prompt Injection）
  ├── 边界场景测试（极端 / 罕见输入）
  ├── 越狱测试（绕过安全约束）
  ├── 误用测试（非预期使用方式）
  └── 压力测试（高并发、长上下文）

红队测试产物：
  ├── 失败案例库 → 进入 Evals 回归集
  ├── 防护规则 → 更新到系统层
  └── 风险清单 → 进入产品风险登记册
```

## 7️⃣ 数据引擎与上下文工程

目标：AI 产品不仅是交互设计，更是数据飞轮的工程设计。本节补足 §4 数据飞轮的工程落地，以及大模型物理约束（上下文窗口）下的设计博弈。

> 📌 本节是 §4 双轨迭代的工程深化，也是 AI 产品区别于传统产品最"脏最累"但最核心的部分。

### Active Learning 数据引擎

> 核心命题：AI 产品的数据飞轮不能靠"用户偶尔点赞点踩"被动收集，必须主动设计数据获取与回流机制。

#### 置信度路由（Human-in-the-Loop）

> ⚠️ 关键校正：**不要直接相信模型自报的置信度**。大模型的 logit 置信度与真实正确性往往弱相关，甚至存在"自信地错"的高风险场景。应使用**经过任务校准的质量/风险估计**作为路由依据，并持续检验阈值的实际表现。

```
模型输出 → 质量估计（校准后的）
              │
              ├── 质量估计 > 阈值高（如 0.9）
              │     └── 自动采用，用户可选修改
              │     └── 修改行为作为隐式反馈
              │
              ├── 质量估计在中间区间（如 0.5-0.9）
              │     └── 给用户预填结果 + 明确提示"需确认"
              │     └── 用户的确认/修改都被记录
              │
              └── 质量估计 < 阈值低（如 0.5）
                    └── 路由给人工处理（或降级到规则）
                    └── 人工结果自动进入标注集
                    └── 形成高质量的训练数据
```

质量估计的来源（不能只用模型自报）：

```
1. 任务校准的置信度
   └── 在标注集上建立"模型置信度 vs 实际正确率"的校准曲线
   └── 用校准后的概率做路由，而非原始 logit

2. 一致性采样
   └── 同一输入多次采样，结果一致 → 质量可能高
   └── 结果分歧大 → 质量估计低，路由给人工

3. 外部验证器
   └── 用专门的判别模型评估输出质量
   └── 比 self-report 更可靠

4. 业务规则校验
   └── 输出是否符合业务约束（格式、范围、引用真实性）
   └── 违反规则直接降级，不论模型多自信

5. 持续阈值检验
   └── 定期检查路由决策的实际准确率
   └── 阈值漂移时及时调整
```

> 设计要点：置信度路由是"成本-质量"的动态平衡。高置信度走自动化降成本，低置信度走人工保质量，中间区间让用户参与同时获取数据。但"置信度"必须是校准后的质量估计，不是模型自报。

#### 主动学习工作流

```
Step 1：模型对未标注数据打分（不确定性采样）
  └── 优先挑选模型最不确定的样本

Step 2：人工标注这些高价值样本
  └── 用最少标注成本获取最大模型提升

Step 3：加入训练集，微调模型
  └── 闭环：模型变强 → 新一轮不确定性采样

Step 4：重复，直到模型达到目标质量
```

#### 冷启动数据策略

```
产品初期没有用户数据怎么办：

合成数据（Synthetic Data）：
  ├── 用强模型生成弱模型的训练数据
  ├── 适合结构化任务（分类、抽取）
  └── 风险：可能继承强模型的偏见

开源数据集：
  ├── HuggingFace、Kaggle 等公开数据集
  ├── 适合通用能力快速起步
  └── 局限：无法覆盖业务特有场景

种子用户标注：
  ├── 内部团队 + 早期用户手动标注
  ├── 质量最高但成本高
  └── 适合核心场景建立 baseline

规则/模板兜底：
  ├── 模型不确定时用规则覆盖
  └── 规则的输出反哺训练数据
```

### 上下文窗口（Context Window）预算管理

> 核心命题：大模型的上下文窗口是有限的物理资源。如何在系统 Prompt、用户输入、RAG 召回、对话历史之间分配 Token 预算，是 AI 产品设计的核心工程约束。

#### Context 预算分解

```
总 Context 预算（如 128K Token）：
  │
  ├── 系统 Prompt（固定开销）
  │     └── 角色定义、能力说明、安全约束
  │     └── 通常 1K-5K Token
  │
  ├── RAG 召回内容（动态，最大变量）
  │     └── 知识库检索的相关文档片段
  │     └── 通常 10K-100K Token
  │
  ├── 对话历史（动态，需管理）
  │     └── 多轮对话的累积上下文
  │     └── 随轮次增长，需主动压缩
  │
  ├── 工具调用结果（动态）
  │     └── API 返回、搜索结果、函数输出
  │     └── 可能很大，需截断或摘要
  │
  └── 用户当前输入 + 模型输出预留
        └── 必须保留足够空间给响应
        └── 通常预留 2K-8K Token
```

#### 召回率 vs 精度的博弈

```
RAG 设计的核心权衡：

召回多（高 Recall）：
  ├── 优势：信息全，少遗漏
  ├── 劣势：Token 消耗大、噪声多、模型可能被干扰
  └── 风险：超出 Context 预算，或"中间遗忘"现象

召回少（高 Precision）：
  ├── 优势：Token 省、信噪比高
  ├── 劣势：可能漏掉关键信息
  └── 风险：回答不完整

平衡策略：
  ├── 分层召回：先粗召回 Top-K，再精排筛选 Top-N
  ├── 多路召回：关键词 + 向量 + 混合，取并集去重
  ├── 摘要压缩：长文档先摘要，按需展开细节
  └── 重排序（Reranker）：用小模型对召回结果精排
```

#### 对话历史管理

```
长对话的 Context 压缩策略：

策略 1：滑动窗口
  ├── 只保留最近 N 轮对话
  └── 简单但可能丢失早期关键信息

策略 2：摘要压缩
  ├── 定期对早期对话生成摘要
  ├── 保留关键决策与用户偏好
  └── 牺牲细节换取长期记忆

策略 3：结构化记忆
  ├── 从对话中抽取结构化信息（用户画像、决策历史）
  ├── 存入外部数据库，按需检索
  └── 最强大但实现复杂

策略 4：分层记忆
  ├── 近期：完整保留
  ├── 中期：摘要保留
  └── 长期：结构化关键信息
```

### 数据飞轮与上下文的协同

```
完整闭环：

用户交互
  ↓
置信度路由（低置信度 → 人工标注）
  ↓
标注数据进入训练集
  ↓
模型微调（提升能力 / 降低成本）
  ↓
更准的召回与更优的 Context 分配
  ↓
更好的用户体验 → 更多交互 → 更多数据
  ↓
（回到顶部，飞轮加速）
```

> 关键洞察：数据飞轮不是"收集数据"那么简单，而是"置信度路由 → 主动学习 → 模型迭代 → Context 优化 → 体验提升"的完整工程闭环。任何一个环节断裂，飞轮就转不起来。

## 8️⃣ 与经典方法论的映射

目标：明确哪些经典方法仍然适用、哪些需要重构、哪些需要新增，避免重复造轮子。

### 仍然适用的方法

```
[[02 产品探索与发现]]
  ├── JTBD 仍然有效（用户雇佣 AI 完成任务）
  ├── 用户研究方法不变
  └── 但要额外研究「用户对 AI 的信任阈值」

[[03 产品构思与设计]]
  ├── 发散-收敛方法不变
  ├── PRD 结构仍然适用
  └── 但需新增「AI 能力边界」章节

[[04 产品度量与数据]]
  ├── AARRR、留存分析仍然适用
  ├── 指标分层体系不变
  └── 但需叠加 Evals 维度（见本模块 §2）

[[06 产品增长与运营]]
  ├── 增长飞轮、激活留存方法不变
  └── 但单位经济模型必须重构（见本模块 §5）
```

### 需要重构的方法

```
[[01 产品商业与战略]]
  ├── 商业模式画布仍适用，但成本结构需重写
  ├── 定价策略需考虑推理成本变量
  └── 差异化护城河从「功能」转向「数据 + 评估 + 调用」

[[03 产品构思与设计#方案验证]]
  ├── 传统可用性测试仍适用
  └── 但需叠加 Evals 验证（质量、安全、成本）

[[05 产品开发与上线]]
  ├── 质量左移原则不变
  ├── 但测试金字塔需重构（加入模型评估层）
  └── 发布策略需增加「模型版本灰度」维度

[[07 产品监控与迭代]]
  ├── 监控体系仍适用
  └── 但需增加「模型质量监控」「成本监控」「安全监控」
```

### 需要新增的方法

```
Evals 体系设计（本模块 §2）—— 经典方法论完全没有
双轨迭代管理（本模块 §4）—— 经典方法论只有单轨
成本结构方法论（本模块 §5）—— 经典方法论假设边际成本为零
AI 安全设计（本模块 §6）—— 经典方法论的安全是边界问题
```

## 阶段卡口（AI 产品专属补充决策门）

> 📌 按决策门规范执行，详见 [[产品方法论总览#阶段卡口 → 决策门规范]]。AI 产品在经典卡口之外，还需回答以下决策门。安全/合规类为 **S 级红线**，其余多为 **A 级**。

1. ✅ 是否建立了分层 Evals 体系，覆盖核心场景？（A 级，L2 证据：Evals 集合 + 基线分数）
2. ✅ 不确定性 UX 是否做到可逆操作 undo、不可逆操作预览+确认+补偿+审计？（A 级，L2 证据：容错设计 Review）
3. ✅ 模型迭代与产品迭代是否解耦管理，升级有回归保护？（A 级，L2 证据：双轨迭代流程 + 回归 Evals）
4. ✅ 推理成本是否纳入单位经济模型，毛利率健康？（A 级，L3 证据：成本测算 + 毛利口径 LTV）
5. ✅ 安全边界是否经过红队测试，关键风险有兜底？（S 级，L3 证据：红队测试报告 + 兜底机制）
6. ✅ 合规要求（备案 / 算法登记 / 隐私）是否前置确认？（S 级，L3 证据：法务意见 + 合规清单）
7. ✅ 数据飞轮是否设计完整（置信度路由 → 主动学习 → 模型迭代闭环）？（A 级，L2 证据：数据飞轮设计文档）
8. ✅ 上下文预算管理策略是否明确（RAG 召回、对话历史、工具结果的 Token 分配）？（A 级，L2 证据：Context 预算方案）
9. ✅ **失败案例分流机制是否建立（不默认进微调）？**（A 级，L2 证据：分流流程 + 处理记录）
10. ✅ **AI 产品的特殊假设（模型能力、成本、安全）已纳入 [[10 决策内核]] 假设台账？**（A 级，L1 证据：假设台账记录）

带风险放行规则：

```
S 级红线（安全/合规）不可带风险放行：
  ├── 红队测试未通过 → 必须修复或限制范围
  ├── 合规未确认 → 不上线
  └── 强行放行需 CEO + 法务双签，并承担监管风险

A 级卡口可条件性放行：
  ├── Evals 基线不完善 → 可灰度小范围上线，持续完善 Evals
  ├── 数据飞轮未完整 → 可先上线收集数据，后续补完闭环
  └── 带风险放行需风险接受人签字 + 灰度 + 告警 + 回滚
```
