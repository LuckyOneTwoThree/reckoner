# 方法论展开

这个模块的核心命题是：​「让正确的东西，被正确地构建出来，并安全地交到用户手中」​。是 PM 协作密度最高、最考验执行力的阶段。

```

```

## 1️⃣ 开发协作与项目管理

目标：让团队在正确的事情上对齐，减少返工和信息损耗

### 敏捷开发框架

> 📌 Sprint 节奏的详细执行规范（两周 Sprint 标准节奏、站会三问原则、Retrospective 流程）见 [[08 项目管理与执行（支撑）#Sprint 执行节奏]]。本节聚焦 PM 在开发协作界面中的角色。

Backlog 管理原则

```
Epic（大功能方向）
  └── Story（用户故事）
        └── Task（开发任务）
              └── Bug（缺陷）
```

用户故事格式

```
作为 [用户角色]
我希望 [完成某件事]
以便 [获得某种价值]

验收标准：
- Given [前置条件]
- When [用户行为]
- Then [系统反应]
```

> 好的用户故事聚焦​用户价值​，不是技术实现——让开发理解「为什么」，而非只是「做什么」

### PM 与开发的协作界面

需求对齐三阶段

```
需求评审（PRD Review）
  → 功能逻辑是否清晰、边界是否明确
        ↓
技术方案评审
  → PM 理解技术约束，开发理解业务逻辑
        ↓
验收标准确认
  → 双方对「完成的定义」达成一致
```

PM 不应该做的事

```
❌ 需求开发中频繁变更（改需求要走流程）
❌ 绕过优先级直接给开发加任务
❌ 对技术方案指手画脚（How 是开发的专业领域）
❌ 验收时才第一次看到功能（要持续介入）
```

需求变更处理流程

```
变更请求
    ↓
评估影响（工期 / 范围 / 质量三角）
    ↓
与 stakeholder 对齐取舍
    ↓
正式更新文档 + 通知相关方
    ↓
重新确认排期
```

### 进度追踪与风险管理

项目健康度四象限

```
        进度正常          进度滞后
风险低   绿灯 ✅           黄灯 ⚠️
风险高   黄灯 ⚠️           红灯 🔴
```

常见风险类型与应对

|风险|信号|应对策略|
|---|---|---|
|需求不清|开发频繁提问|补充文档、组织澄清会|
|技术复杂度低估|工期持续 delay|评估裁减范围或顺延|
|依赖阻塞|等待其他团队|提前识别依赖，主动推进|
|关键人力缺失|核心成员请假离职|备份文档，知识共享|

缓冲时间策略

```
不要在每个任务加 buffer → 会被帕金森定律消耗掉
而是在里程碑节点集中设置 buffer → 更有效保护交付日期
```

## 2️⃣ 质量保障

目标：质量不是测试出来的，而是设计和开发进去的

### 质量左移原则

```
传统模式：开发完 → 测试 → 发现问题 → 修复（成本高）

质量左移：需求阶段 → 设计阶段 → 开发阶段 → 测试
          逐步内建质量，越早发现越便宜
```

PM 在质量保障中的角色

```
需求阶段：写清楚验收标准，减少理解歧义
设计阶段：Review 边界场景和异常流程
开发阶段：及时澄清问题，避免猜测实现
测试阶段：参与核心场景验收，而非全量测试
```

### 测试策略体系

测试金字塔

```
          / E2E 测试 \          （少量，覆盖核心流程）
        /  集成测试   \         （适量，验证模块协作）
      /   单元测试     \        （大量，快速、低成本）
```

PM 需要参与的测试类型

|测试类型|PM 参与度|关注点|
|---|---|---|
|功能验收测试|高|是否符合需求和验收标准|
|探索性测试|中|用户视角发现意外问题|
|回归测试|低|确保老功能未被破坏|
|性能测试|低|关注结果，不参与执行|

验收测试执行框架

```
核心路径验收：Happy Path（正常流程完整走通）
        ↓
边界场景验收：Edge Cases（极端输入、异常状态）
        ↓
异常场景验收：Error States（网络断开、权限不足）
        ↓
跨端验收：iOS / Android / Web 表现一致性
        ↓
性能验收：加载时长、响应速度达到预设标准
```

### Bug 管理流程

Bug 严重程度分级

```
P0 致命：核心功能不可用，需立即修复（当日）
P1 严重：主要功能异常，影响用户使用（24-48h）
P2 一般：次要功能问题，有 workaround（本 Sprint）
P3 轻微：体验问题、文案错误（排期修复）
```

上线卡口：Bug 清零标准

```
P0、P1 全部修复 → 可以上线
P2 修复率 > 80% → 可以上线，剩余排下期
P3 可带病上线，记录跟踪
```

## 3️⃣ 发布策略

目标：控制发布风险，让好功能安全地到达用户

### 发布策略选择

灰度发布（Canary Release）

```
1% 用户 → 观察数据 → 正常
    ↓
10% 用户 → 观察数据 → 正常
    ↓
50% 用户 → 观察数据 → 正常
    ↓
100% 全量
```

> 每个阶段设置观察期和​回滚阈值​，异常立即回滚

功能开关（Feature Flag）

```
优势：
- 代码已上线，功能未开放 → 解耦发布与部署
- 可针对特定用户群开启  → 精准灰度
- 出问题可秒级关闭      → 无需回滚代码

适用场景：
- 大功能分批开放
- A/B 测试分流控制
- 重要节点紧急熔断
```

蓝绿部署 vs 滚动更新

```
蓝绿部署：新旧环境同时运行，流量一键切换，回滚快
滚动更新：逐步替换实例，资源消耗少，适合无状态服务
金丝雀部署：少量流量先切新版，等同于灰度发布
```

### 上线 Checklist

发布前（T-7天）

```
- [ ] PRD 最终版本确认，无未解决的需求歧义
- [ ] 所有 P0/P1 Bug 修复完成
- [ ] 埋点验证完成，数据可正常采集
- [ ] 监控告警配置完成（阈值设置合理）
- [ ] 回滚方案已准备，回滚步骤有文档
- [ ] 客服团队已培训，FAQ 已准备
- [ ] 合规检查通过（数据隐私/内容审核/未成年人保护/资质许可，按产品类型勾选适用项）
```

发布前（T-1天）

```
- [ ] 灰度环境验证通过
- [ ] 相关团队（运营、客服、销售）已知会
- [ ] 发布时间窗口确认（避开业务高峰）
- [ ] 应急联系人已确认，on-call 安排就绪
```

发布中

```
- [ ] 按灰度计划逐步放量
- [ ] 核心指标实时监控（转化、留存、崩溃率）
- [ ] 用户反馈渠道持续监听
- [ ] 每个灰度阶段有明确的观察时间窗口
```

发布后（T+24h / T+72h）

```
- [ ] 核心指标与 baseline 对比
- [ ] 异常 Bug 是否出现
- [ ] 用户反馈舆情是否正常
- [ ] 是否达到预设放量条件
```

### 沟通发布计划

发布通知模板

```
【功能名称】上线通知

上线时间：
影响范围：（哪些用户 / 哪些端）
功能概述：（一句话说清楚做了什么）
预期效果：（对指标的预期影响）
监控指标：（重点观察什么）
回滚方案：（如有问题如何处理）
负责人：
```

## 4️⃣ 上线复盘

目标：让每次发布成为组织学习的机会，而非结束

### 复盘框架

上线效果复盘（T+2周）

```
1. 目标达成情况
   预期指标 vs 实际指标，差距分析

2. 用户反馈归纳
   正向反馈 / 负向反馈 / 未预期反馈

3. 工程质量评估
   Bug 数量 / 严重度 / 修复效率

4. 发布过程复盘
   是否顺利 / 遇到什么问题 / 如何解决
```

项目过程复盘（Retrospective）

四维复盘法

```
✅ 做得好的（继续保持）
⚠️ 做得不够的（下次改进）
💡 新的尝试（下次可以试试）
❓ 仍然困惑的（需要进一步探索）
```

### 复盘到行动的转化

```
复盘结论
    ↓
提炼可行动的改进项（Actionable Items）
    ↓
指定负责人 + 截止时间
    ↓
下次复盘时检查落实情况
```

> ⚠️ 复盘最常见的失败模式：形成了文档，没有形成改变

### 功能效果评估框架

```
短期效果（T+1周）：
  功能使用率、关键路径转化、崩溃率

中期效果（T+1月）：
  对留存指标的影响、用户 LTV 变化

长期效果（T+1季度）：
  是否达成 OKR、对北极星指标的贡献
```

## 5️⃣ 产品上市与团队赋能（GTM）

目标：产品上线 ≠ 交付完成。让销售、运营、客服、市场能正确理解和承接产品，是产品从"能用"到"被市场接受"的关键一跃。

> 📌 本环节是 [[05 产品开发与上线]] 与 [[06 产品增长与运营]] 之间的关键卡口。B 端/SaaS/复杂产品尤其重要，C 端轻量产品可裁剪。

### GTM 本质：从"产品交付"到"市场交付"

```
产品交付（PM 完成）          市场交付（GTM 完成）
─────────────                ─────────────
功能已上线                    市场能听懂价值
开发已验收                    销售能讲清差异
埋点已就绪                    客服能答常见问题
                              运营能承接用户
                              目标客户已知悉
```

### Product Marketing 三件套

#### 1. 定位与传播信息（Messaging）

```
核心产出：一页纸 Messaging House

  产品定位（一句话）：
    对于 [目标客户]，[产品名] 是 [品类]，
    帮助 [核心价值]，不同于 [主要竞品]，我们 [差异化]

  价值主张分层：
    ├── 一句话版本（电梯演讲，< 15 秒）
    ├── 段落版本（邮件/官网首屏，< 100 字）
    └── 详细版本（销售手册/白皮书）

  关键卖点（3-5 个）：
    ├── 卖点 → 对应客户痛点 → 证据（数据/案例/演示）
    └── 避免"功能罗列"，要讲"客户获得什么"

  反对意见预案：
    ├── 客户最可能的 3 个顾虑
    └── 标准应对话术
```

#### 2. 内部赋能（Enablement）

```
按角色定制赋能内容：

销售团队：
  ├── 产品价值话术（不是功能介绍）
  ├── 竞品对比Battle Card
  ├── 典型客户案例与演示场景
  ├── 定价与折扣权限说明
  └── 常见异议处理手册

客服团队：
  ├── FAQ 与知识库
  ├── 常见问题排查树
  ├── 升级流程（什么问题转给谁）
  └── 用户反馈收集模板（反哺产品）

运营团队：
  ├── 用户运营策略与节奏
  ├── 活动文案审核要点
  ├── 数据监控 Dashboard 使用培训
  └── 异常情况应急预案

市场团队：
  ├── 品牌叙事与传播节奏
  ├── 内容素材包（截图、视频、案例）
  ├── 媒体/PR 关键信息点
  └── 行业大会/活动接入计划
```

#### 3. 上市节奏（Launch Plan）

```
上市策略选择（按产品重要性）：

全功能发布（Full Launch）：
  ├── 适用：重大战略产品、新版本
  ├── 节奏：发布会 + 媒体全覆盖 + 销售全员推动
  └── 风险：声量大但准备不足会反噬

软启动（Soft Launch）：
  ├── 适用：验证市场反馈的中小功能
  ├── 节奏：老用户优先 + 口碑传播 + 逐步放量
  └── 优势：低风险、可调整

分阶段发布（Phased Rollout）：
  ├── 适用：复杂产品、多客户类型
  ├── 节奏：种子客户 → 标杆客户 → 行业推广 → 全量
  └── 优势：每阶段积累案例反哺下阶段

沉默发布（Silent Release）：
  ├── 适用：体验优化、技术重构、小功能
  ├── 节奏：直接上线，不做市场动作
  └── 优势：低调验证，避免过度承诺
```

### GTM 卡口（进入 06 增长运营的条件）

```
✅ Messaging 已对齐，销售/客服能复述产品价值？
✅ 关键团队已培训，有 FAQ 与 Battle Card？
✅ 上市策略已选定，节奏与责任人明确？
✅ 客户反馈渠道已就绪，能承接市场响应？
✅ 标杆客户/种子案例已有（B 端）或冷启动策略已定（C 端）？
```

> ⚠️ 跳过 GTM 直接做增长的常见反模式：销售拿着旧话术卖新功能、客服答不上用户问题、市场传播与产品实际价值错位——产品再好也接不住流量。

## 阶段卡口（决策门）

> 📌 按决策门规范执行，详见 [[产品方法论总览#阶段卡口 → 决策门规范]]。本卡口等级：**S 级 + A 级混合**。P0 Bug 与安全合规是 S 级红线，GTM 是 A 级。

进入循环三的增长阶段之前，需要回答：

1. ✅ 功能已通过验收测试，P0 Bug 清零？（S 级，L3 证据：QA 报告 + 验收签字）
2. ✅ P1 Bug 是否清零或带风险放行？（S 级默认不放行；带风险放行需风险接受人签字 + 灰度 + 告警 + 回滚条件）
3. ✅ 安全合规检查通过？（S 级，L3 证据：合规 Checklist + 法务签字）
4. ✅ 埋点数据可正常采集，监控 Dashboard 就绪？（A 级，L2 证据：数据验证）
5. ✅ 灰度发布顺利，核心指标无异常？（A 级，L3 证据：灰度数据 + 对比基线）
6. ✅ GTM 准备就绪（销售/客服/运营已赋能）？（A 级，L2 证据：培训记录 + Battle Card）
7. ✅ 上线后用户反馈已收集，无重大负面问题？（A 级，L2 证据：反馈渠道 + 数据）
8. ✅ 完成上线复盘，改进项已记录？（B 级，L1 证据：复盘文档）
9. ✅ **上线决策已写入 [[10 决策内核]] 决策记录？**（A 级，L1 证据：DR 文档）

P1 带风险放行的标准格式（重要）：

```
不能机械地"P1 全部修复才能上线"。P1 是否可带风险上线，由以下决策决定：

风险接受人：______________________（签字）
风险描述：______________________
风险等级：低 / 中 / 高
补偿措施：
  ├── 灰度范围：______________________
  ├── 告警阈值：______________________
  ├── 回滚条件：______________________
  └── 修复时限：______________________
复核日期：______________________

→ 接入 [[10 决策内核]] 决策记录存档
```
