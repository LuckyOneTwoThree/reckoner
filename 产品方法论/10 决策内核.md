# 10 决策内核

> 📌 定位：这是整套方法论的**操作系统**，而非又一个框架。它定义全体系共用的最小决策对象——产品论点、假设台账、机会树、决策记录。所有模块（01-09）的框架和卡口都挂在这些对象上，避免"文档很多、决策仍靠会议记忆"的反模式。

## 为什么需要决策内核

传统方法论的失效模式：

```
反模式 1：文档很多，决策仍靠会议记忆
  ├── PRD 写了 50 页，但没人记得为什么做这个功能
  ├── 半年后回看，找不到当时的决策依据
  └── 新人接手只能靠口口相传

反模式 2：假设被默认为事实
  ├── "用户需要这个功能"——谁验证的？什么证据？
  ├── "这个商业模式可行"——基于什么假设？
  └── 假设没显式化，错了也无法纠偏

反模式 3：技术/合规验证后置
  ├── 产品做完才发现接不了某个 API
  ├── 上线前才发现合规过不了
  └── B 端/AI 产品尤其致命——做出来才发现不能卖、不能接、不能上线

反模式 4：决策无追溯
  ├── 为什么放弃了方案 A？
  ├── 为什么选了渠道 X 而不是 Y？
  └── 没有记录，无法复盘，无法学习
```

决策内核解决这些问题：把产品工作显式化为可追溯的**假设-证据-决策**链路。

## 四个核心对象

### 对象 1：产品论点（Product Thesis）

> 一段话陈述"我们为什么做这个产品/功能"。所有后续工作的北极星。

最小字段：

```
产品论点模板
├── 目标用户：是谁（具体到可识别的群体）
├── 待完成任务（JTBD）：用户想达成什么
├── 独特价值：我们提供什么独特帮助
├── 为什么现在做：时机依据（市场变化、技术成熟、需求爆发）
└── 战略边界：不做什么、不服务谁、不碰哪些场景
```

示例：

```
产品论点（某 AI 写作助手）
├── 目标用户：内容创作者（公众号作者、自媒体运营）
├── 待完成任务：在保证质量的前提下，提升内容产出效率
├── 独特价值：基于用户已有内容风格生成，保持个人 voice
├── 为什么现在做：大模型能力成熟 + 创作者经济爆发
└── 战略边界：
     ├── 不做通用聊天机器人
     ├── 不服务企业级内容工厂
     └── 不替代创作者判断，只做辅助
```

使用规则：

```
├── 每个产品/重大功能立项时必写
├── 评审时第一件事就是确认产品论点
├── 后续所有方案必须能回溯到产品论点
└── 产品论点变化 = 重大战略调整，需重新评审
```

### 对象 2：假设台账（Assumption Ledger）

> 把产品论点拆解为可验证的假设，分类管理。这是决策内核最核心的对象。

四类假设（必须分类，因为验证方式不同）：

```
┌─────────────────────────────────────────────────────┐
│ 类别 A：用户价值假设                                  │
│   "用户真的有这个痛点吗？真的愿意为此付费/改变行为吗？" │
│   验证方式：用户访谈、原型测试、MVP 数据               │
│   证据来源：定性为主，定量辅助                          │
├─────────────────────────────────────────────────────┤
│ 类别 B：商业可行性假设                                 │
│   "这个模式能赚钱吗？单位经济成立吗？"                 │
│   验证方式：单位经济模型、定价测试、渠道验证             │
│   证据来源：定量为主，市场参考辅助                      │
├─────────────────────────────────────────────────────┤
│ 类别 C：技术可行性假设                                 │
│   "我们能做出来吗？性能/成本/集成可行吗？"              │
│   验证方式：技术验证 PoC、性能压测、成本测算             │
│   证据来源：工程实验数据                                │
├─────────────────────────────────────────────────────┤
│ 类别 D：安全/合规假设                                  │
│   "能上线吗？会触犯什么监管？数据合规吗？"              │
│   验证方式：法务评审、合规检查清单、监管沟通             │
│   证据来源：法务/合规意见、监管文件                     │
└─────────────────────────────────────────────────────┘
```

最小字段：

```
假设台账单条记录
├── 假设编号：A-001
├── 假设类型：用户价值 / 商业可行 / 技术可行 / 安全合规
├── 假设陈述：明确、可证伪的命题
├── 证据强度：
│     ├── 未验证（猜想）
│     ├── L1 弱证据（个别访谈样本<5人、推理、专家主观判断）
│     ├── L2 中等证据（小规模实验样本<100、原型测试通过、技术 PoC 跑通）
│     ├── L3 强证据（A/B 实验统计显著 p<0.05、上线灰度数据、法务安全正式邮件签批）
│     └── L4 共识证据（大规模放量数据如财报级、高管会正式决议）
├── 错了的代价：
│     ├── 低：错了可快速回滚
│     ├── 中：错了需返工，影响一个版本
│     └── 高：错了影响产品存亡或合规风险
├── 负责人：明确到个人
├── 最低成本验证方式：如何在最少投入下证伪/证实
├── 停止阈值：什么证据下放弃这个假设
├── 扩大阈值：什么证据下扩大投入
└── 当前状态：待验证 / 验证中 / 已证实 / 已证伪 / 已废弃
```

关键原则：

```
原则 1：显式化与免检阈值（降阻机制）
  ├── 并非所有需求都需要写台账。预期研发 < 10 人日或低风险体验优化，适用“免检原则”，跳过台账。
  ├── 高风险、高代价项目必须显式化，隐藏假设 = 隐藏风险。
  └── 提倡由 Agent（如假设拆解工作流）通过 PRD 逆向推导并生成假设，PM 仅做审核确认，将“创建者”摩擦降为“编辑者”。

原则 2：按代价排序验证
  ├── 错了代价高的假设优先验证
  ├── 不要先验证容易的，要先验证致命的
  └── 尤其 D 类（合规）必须前置，不能后置

原则 3：证据强度要诚实
  ├── "我觉得"不等于证据
  ├── "老板说"不等于证据
  └── 个别用户访谈只是弱证据，不能当强证据用

原则 4：假设会演化
  ├── 验证后更新证据强度
  ├── 证伪后要么调整方案，要么调整假设
  └── 假设台账是活文档，不是一次性产出
```

### 对象 3：机会方案树（OST）

> 详见 [[02 产品探索与发现#机会方案树（OST）—— 从探索到构思的桥梁]]。此处只列其在决策内核中的角色。

在决策内核中的定位：

```
OST 连接假设与行动
├── Outcome：源自产品论点和北极星指标
├── Opportunity：来自用户价值假设的验证
├── Solution：对应技术/商业假设的验证对象
└── Experiment：假设验证的执行方式
```

每个 Solution 必须挂载对应的假设编号：

```
Solution（新手引导方案 A）
├── 验证假设：A-003（新用户不知道下一步做什么）
├── 验证假设：B-002（提升 D7 留存可改善单位经济）
└── 实验：A/B 测试，2 周，D7 留存 +3% 为扩大阈值
```

### 对象 4：决策记录（Decision Record）

> 重大决策的留档。未来可复盘、可追溯、可学习。

最小字段：

```
决策记录模板
├── 决策编号：DR-2026-007
├── 决策日期：YYYY-MM-DD
├── 决策内容：做了什么决定（做/不做/选 A 不选 B）
├── 决策类型：
│     ├── Type 1（不可逆）：慎重决策
│     └── Type 2（可逆）：快速试错
├── 依据：支撑该决策的假设与证据（【强制要求】所有证据必须附带可跳转的实体链接/锚点，如数据看板 URL、法务邮件截图）
├── 反证：当时考虑过但被否决的方案与原因
├── 预期结果：决策后预期发生什么（可量化）
├── 复盘日期：何时回来检查决策效果
├── 实际结果：（复盘时填写）
└── 决策人：明确到个人（不是"团队决定"）
```

何时写决策记录：

```
必须写的场景：
├── 放弃某个方案
├── 选择某个技术栈/供应商/渠道
├── 调整产品方向
├── 重大功能上线/下线决策
├── 定价调整
└── 资源分配重大变化

不必写的场景：
├── 日常小决策（按钮颜色、文案措辞）
├── 执行层面的选择
└── 可逆且低成本的尝试
```

## 四个对象的串联关系

```
产品论点（战略层）
    │
    │ 拆解为
    ↓
假设台账（验证层）
    │
    │ 通过实验验证
    ↓
机会方案树（行动层）
    │
    │ 实验后形成
    ↓
决策记录（沉淀层）
    │
    │ 复盘后回流修正
    ↓
产品论点 / 假设台账（形成闭环）
```

## 阶段卡口（决策内核专属）

```
✅ 产品立项时，是否已写出产品论点（5 要素齐全）？
✅ 是否已识别四类假设，并按代价排序？
✅ 高代价假设（尤其安全/合规类）是否已前置验证？
✅ OST 每个 Solution 是否挂载了对应假设编号？
✅ 重大决策是否已写决策记录（含反证与复盘日期）？
✅ 是否定期复盘决策记录，更新假设台账的证据强度？
```

## 实施建议

### 轻量起步

```
不要一开始就上重型流程：
├── 第 1 周：只写产品论点（一页纸）
├── 第 2 周：识别 Top 5 最关键假设，开始验证
├── 第 3 周：用 OST 组织当前正在做的方案
└── 第 4 周：从这周开始，所有重大决策写决策记录
```

### 工具选择

```
轻量级（推荐起步）：
├── 飞书文档 / Notion / Obsidian（结构化模板）
├── 假设台账用表格（清晰易维护）
└── 决策记录用专门文件夹/标签管理

中量级（团队规模扩大后）：
├── Productboard / Productive（专门的产品管理工具）
├── 假设台账与需求管理工具打通
└── 决策记录接入知识库
```

### 反模式警示

```
❌ 假设台账变成"应付流程"
   → 只写不验证，台账成了摆设
   → 对策：每周 Review 一次假设状态

❌ 决策记录写成"决策结果"
   → 只记做了什么，不记为什么
   → 对策：必须包含"反证"和"预期结果"

❌ 把所有假设都同等对待
   → 平摊资源，致命假设被忽视
   → 对策：按"错了的代价"排序，优先验证高代价

❌ 安全/合规假设后置
   → 做完才发现不能上线
   → 对策：D 类假设必须前置，立项阶段就验证
```

## 与方法论总览的关系

本模块是 [[产品方法论总览#主链路：非线性三循环模型]] 的横切层。三循环中的每个循环入口和出口，都通过决策内核的对象串联：

```
循环一（意图与探索）
  ├── 入口：写出产品论点
  ├── 过程：探索验证用户价值假设
  └── 出口：假设台账 + OST 形成可执行方案

循环二（方案与验证）
  ├── 入口：带着假设进入方案设计
  ├── 过程：方案对应假设，实验收集证据
  └── 出口：决策记录沉淀验证结果

循环三（交付与增长）
  ├── 入口：基于强证据的方案进入交付
  ├── 过程：上线数据持续验证商业假设
  └── 出口：监控触发假设重评，回流到循环一/二
```

> 关键洞察：决策内核不是"又一个文档要求"，而是把产品工作从"做功能"升级为"做决策"的元机制。没有它，方法论是参考手册；有了它，方法论是操作系统。
