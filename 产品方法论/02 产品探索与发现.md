# 方法论展开

这个模块的核心命题是：​「发现真实问题，而非假设问题」​。可以拆成 4 个子模块：

---

## 模块结构总览

```
产品探索与发现
├── 0. 信号池（Signal Pool）与原始洞察
├── 1. 用户研究
├── 2. 需求分析与洞察
├── 3. 市场与竞品分析
└── 4. 机会识别与定义
```

---

## 0️⃣ 信号池（Signal Pool）与原始洞察

目标：从海量的、混沌的市场噪音和用户抱怨中，收敛出值得被研究的“产品论点”起点。

### 核心概念：Signal -> Cluster -> Thesis
- **Signal（信号）**：一条原始的用户反馈、一个竞品动作、一个技术趋势。它是非结构化的。
- **Cluster（聚类）**：当多个 Signal 指向同一痛点时，形成聚类。
- **状态流转**：当一个 Cluster 的热度（频次、影响面）越过阈值时，正式孵化为一个新的“产品论点（Product Thesis）”，进入正式的探索循环。

> 💡 建议接入 Agent 工作流（见 [[11 Agent工作流与自动化落地]]）来执行全天候雷达监控，自动将应用商店评论、客服聊天记录等文本进行聚类，自动提炼出可能的产品论点草案。

## 1️⃣ 用户研究

目标：理解用户是谁、他们的行为和动机

### 定性方法

|方法|适用场景|关键要点|
|---|---|---|
|深度访谈（User Interview）|探索动机、痛点|问「为什么」而非「要什么」|
|情境调查（Contextual Inquiry）|观察真实使用行为|去用户现场，而非会议室|
|焦点小组（Focus Group）|收集集体态度|注意群体压力影响真实性|
|日记研究（Diary Study）|了解长期行为变化|适合低频但重要的场景|

### 定量方法

- ​问卷调查​：大规模验证假设，注意避免引导性提问
- ​行为数据分析​：埋点、漏斗、热力图——用户「说的」vs「做的」
- ​NPS / CSAT​：感知满意度基线

### 用户建模工具

- ​Persona（用户画像）​：基于研究而非拍脑袋，需包含目标、行为、痛点
- ​Empathy Map（同理心地图）​：说/想/做/感，快速对齐团队认知
- ​User Journey Map（用户旅程图）​：全链路体验可视化，找情绪低谷点

## 2️⃣ 需求分析与洞察

目标：把表层需求转化为本质洞察

### 核心框架

Jobs To Be Done（JTBD）

> 用户不是在买产品，而是在「雇佣」产品完成某项任务
> 
> - Functional Job：功能性目标
> - Emotional Job：情感性目标
> - Social Job：社会性目标

需求三层模型

```
表层需求（用户说的）
    ↓
行为需求（用户做的）
    ↓
本质需求（用户想的）← 产品价值在这里
```

​5 Whys 分析​：持续追问「为什么」，穿透表象到根因

### 需求优先级判断

- ​KANO 模型​：区分必备 / 期望 / 兴奋型需求
- 痛点 × 频率 × 可解决性 矩阵：评估值不值得做

---

## 3️⃣ 市场与竞品分析

目标：理解外部环境，找到差异化空间

### 市场分析

- ​TAM / SAM / SOM​：市场规模测算，判断天花板
- ​PEST 分析​：政治、经济、社会、技术趋势扫描
- ​行业生命周期判断​：新兴 / 成长 / 成熟 / 衰退——影响策略选择

### 竞品分析框架

```
竞品分析四象限
├── 直接竞品（同场景同方案）
├── 间接竞品（同场景不同方案）
├── 替代方案（用户现在怎么解决的）
└── 潜在竞品（可能进来的玩家）
```

​分析维度​：功能对比 / 用户口碑 / 商业模式 / 增长策略 / 产品定位

​工具​：Feature Matrix、竞品体验拆解、App 评论挖掘（AppFollow、七麦）

---

## 4️⃣ 机会识别与定义

目标：从信息噪音中找到值得押注的机会

### 机会评估框架

机会评分矩阵

| 维度    | 问题          |     |
| ----- | ----------- | --- |
| 问题真实性 | 用户真的有这个痛点吗？ |     |
| 市场规模  | 有多少人有这个问题？  |     |
| 解决可行性 | 我们有能力做吗？    |     |
| 战略契合度 | 这符合我们的方向吗？  |     |
| 竞争壁垒  | 我们做有差异化优势吗？ |     |

​How Might We（HMW）​：将问题转化为机会陈述，驱动发散思考

### 机会方案树（OST）—— 从探索到构思的桥梁

> 📌 本节是衔接 [[03 产品构思与设计]] 的关键工具。传统需求池是二维列表，容易变成 Feature 堆砌；OST 强制把所有方案挂在业务目标下，做到绝对的战略对齐。源自 Teresa Torres 的 Continuous Discovery 方法。

OST 结构

```
              北极星指标 / 业务 Outcome
                       │
        ┌──────────────┼──────────────┐
        │              │              │
    机会 1           机会 2           机会 3
   （用户痛点/      （用户痛点/      （用户痛点/
    未满足需求）      未满足需求）      未满足需求）
        │              │              │
    ┌───┼───┐      ┌───┴───┐      ┌───┴───┐
   方案  方案  方案  方案    方案    方案    方案
    A    B    C    D      E      F      G
        │              │
     实验 1          实验 2
   （MVP/测试）    （MVP/测试）
```

OST 四层定义

```
Outcome（结果层）
  └── 业务想达成的可量化结果，对应北极星指标
  └── 例：提升 D7 留存率 5%

Opportunity（机会层）
  └── 用户在达成目标过程中的痛点、需求、未满足场景
  └── 来自用户研究，是"问题空间"，不是方案
  └── 例：新用户首次使用后不知道下一步做什么

Solution（方案层）
  └── 针对某个机会的具体解决方案
  └── 一个机会可对应多个方案，先发散再收敛
  └── 例：新手引导 / 默认内容推荐 / 朋友动态预填

Experiment（实验层）
  └── 验证方案假设的最小测试
  └── 原型、MVP、A/B 测试、落地页测试
```

OST 使用原则

```
原则 1：先有 Outcome，再有 Opportunity
  └── 永远从业务结果倒推，不要从"我想做个功能"正推

原则 2：Opportunity 是问题，不是方案
  └── "用户找不到入口"是 Opportunity
  └── "加个浮动按钮"是 Solution，不要混到 Opportunity 层

原则 3：一个 Opportunity 至少发散 3 个 Solution
  └── 避免第一个想法直接上（呼应 [[03 产品构思与设计]] 先发散再收敛）

原则 4：Solution 必须挂实验
  └── 没有验证计划的方案只是猜想
  └── 实验是最小成本验证假设的方式

原则 5：OST 是活文档，持续迭代
  └── 不是一次性画完，而是 Continuous Discovery 的持续产出
  └── 每周访谈用户后更新 Opportunity，每轮迭代更新 Solution
```

Continuous Discovery 双轨并行

```
传统模式（线性）：探索 → 交付 → 探索 → 交付（割裂）
双轨模式（并行）：
  探索轨道：持续访谈用户、更新 OST、准备下轮实验
  交付轨道：执行当前 Sprint、上线、监控
  └── 两条轨道同时运行，互不阻塞

PM 时间分配：
  ├── 每周至少 2-3 次用户接触（哪怕只是 15 分钟访谈）
  ├── 持续更新 OST，而非每季度做一次大研究
  └── 探索的产出喂养交付，交付的反馈反哺探索
```

### 交付物定义

探索阶段最终需要产出：

> - ​Problem Statement​：清晰定义「为谁解决什么问题，当前方案为何不够好」
> - ​机会简报（Opportunity Brief）​：对齐团队和 stakeholder，作为进入下一阶段的入场券

## 阶段卡口（决策门）

> 📌 按决策门规范执行，详见 [[产品方法论总览#阶段卡口 → 决策门规范]]。本卡口等级：**S 级**（用户问题真实性是红线，不可降级）。必须达到 L3 强证据，由产品负责人 + 风险接受人双签。

进入循环二（方案与验证）之前，需要回答（S 级红线）：

1. ✅ 我们在为谁解决什么问题？（L3 证据：≥5 次深度用户访谈，含需求验证）
2. ✅ 这个问题真实存在且足够重要？（L3 证据：用户行为数据或重复反馈，非孤例）
3. ✅ 现有方案为何不够好？（L2 证据：竞品分析 + 用户痛点陈述）
4. ✅ 这个机会对我们值得押注？（L2 证据：机会简报，含市场/竞争/资源分析）

带风险放行规则：

```
S 级卡口原则上不可带风险放行。如确需在信息不全时前进：
  ├── 必须由产品负责人 + 风险接受人双签
  ├── 必须明确补充验证的时间窗口（通常 ≤ 2 周）
  ├── 必须设定"证伪即停"的退出条件
  └── 必须接入 [[10 决策内核]] 决策记录
```
