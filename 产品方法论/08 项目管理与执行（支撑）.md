# 方法论展开

这个模块的核心命题是：​「再好的战略和设计，没有扎实的执行都是空中楼阁」​。它不是独立阶段，而是贯穿所有模块的底层能力，决定团队能否持续、高质量地交付。

---

## 模块结构总览

```
项目管理与执行（支撑层）
├── 1. 执行体系与节奏管理
├── 2. 跨职能协作
├── 3. 沟通与信息管理
└── 4. 个人执行力与 PM 效能
```

---

## 1️⃣ 执行体系与节奏管理

目标：建立可预期、可持续的交付节奏，让团队在清晰的结构中高效运转

### 执行体系分层

```
战略层（季度）
  OKR 制定 → 路线图规划 → 资源对齐
        ↓
战术层（月）
  Epic 拆解 → 里程碑设定 → 跨团队协调
        ↓
执行层（周）
  Sprint 规划 → 任务分配 → 日常推进
        ↓
操作层（日）
  站会同步 → 阻塞清除 → 当日交付
```

> 大多数执行问题来自​层级断裂​——战略清晰但落不到周任务，或日常忙碌但偏离季度目标

### 季度规划节奏

Season Planning 流程

```
T-3周：数据回顾
  └── 上季度 OKR 完成情况
  └── 核心指标趋势分析
  └── 用户反馈归纳

T-2周：方向对齐
  └── 下季度战略重点讨论
  └── 与上级 / 业务方对齐
  └── 草拟 OKR 框架

T-1周：资源规划
  └── 人力 / 时间估算
  └── 依赖识别与协调
  └── OKR 最终确认

T-0：季度启动
  └── 全团队同步
  └── 路线图发布
  └── 第一个 Sprint 规划
```

### Sprint 执行节奏

两周 Sprint 标准节奏

```
Day 1（周一上午）Sprint Planning
  └── 回顾 Backlog 优先级
  └── 团队认领任务，估算工作量
  └── 确认 Sprint Goal

Day 1-9  Sprint 执行
  └── 每日站会（15分钟，不超时）
  └── PM 持续可用，及时澄清需求
  └── 阻塞当日解决，不过夜

Day 9（周五下午）Sprint Review
  └── 演示完成的功能
  └── 验收 + 反馈收集
  └── 未完成项评估原因

Day 10（下周一上午）Retrospective
  └── 流程改进讨论（< 1小时）
  └── 改进项指定负责人
  └── 紧接 Next Sprint Planning
```

### 技术债管理与团队呼吸

> ⚠️ 纯 Feature Factory（特性工厂）模式会让团队疲劳、代码腐化、迭代速度持续下降。健康的执行节奏必须显式管理技术债。

技术债带宽强制分配

```
每个 Sprint 强制拨出 15%-20% 工程带宽给技术债：

  └── 类型 1：偿还型（主动）
      ├── 重构脏代码、补测试、补文档
      └── 由工程师自主识别和领取

  └── 类型 2：预防型（主动）
      ├── 升级依赖、性能优化、可观测性建设
      └── 由技术负责人规划

  └── 类型 3：应急型（被动）
      ├── 紧急 Bug、线上故障
      └── 计入但不应占用主动带宽

PM 的角色：
  ├── 在 Sprint Planning 显式保留技术债容量
  ├── 不允许业务需求挤占技术债带宽（除非 P0 紧急）
  └── 把技术债偿还视为投资，不是成本
```

> 这是高级 PM 建立技术信任最硬核的手段。工程师感受到"PM 在保护我们的代码质量"，信任自然建立。

Shape Up（可选节奏）

> Basecamp 的替代节奏，适合独立产品、小团队、对深度工作要求高的场景。不强制替代 Sprint，作为可选模式参考。

```
Shape Up 节奏（6 周 + 2 周）：

  Betting Phase（下注期，2 天）
    └── 团队共同评估 Pitch（成型的方案）
    └── 决定下个周期做哪 1-2 个

  Build Phase（构建期，6 周）
    └── 全力执行，禁止中途加需求
    └── 团队自主决定如何做

  Cool-down（冷静期，2 周）
    └── 偿还技术债
    └── 自发创新与探索
    └── Bug 修复与体验打磨
    └── 为下个 Betting Phase 准备 Pitch

适用条件：
  ✓ 产品可独立，跨团队依赖少
  ✓ 团队成熟，可自主管理
  ✓ 功能价值大，值得 6 周深耕
  ✗ 不适合：依赖密集、紧急响应多的场景
```

两种节奏的选择

```
两周 Sprint：
  ├── 优势：节奏快、反馈快、适合持续优化
  ├── 劣势：容易陷入特性工厂、深度工作被打断
  └── 适用：迭代优化、Bug 修复、中小功能

Shape Up：
  ├── 优势：深度工作、团队自主、避免碎片化
  ├── 劣势：反馈周期长、不适合紧急场景
  └── 适用：重大功能、产品重设计、需要深耕的方向

混合策略：
  ├── 主线用 Shape Up（重大方向深耕）
  ├── 支线用 Sprint（优化、Bug、小需求）
  └── 冷静期统一用于技术债与创新
```

站会三问原则

```
昨天完成了什么？（进展）
今天计划做什么？（计划）
有什么阻塞需要帮助？（障碍）

注意：
  站会是同步信息，不是汇报工作
  讨论解决方案放到站会后小组讨论
  PM 角色：听障碍，会后立即跟进解决
```

### 里程碑管理

里程碑设计原则

```
每个里程碑应该是：
  ├── 可验证的（有明确的完成标准）
  ├── 有业务意义的（不只是技术节点）
  ├── 间隔合理的（2-4周一个检查点）
  └── 与外部承诺对齐的（发布日、商务节点）
```

关键路径管理

```
识别关键路径：
  └── 找出影响最终交付日期的任务链
  └── 关键路径上的任何延误直接影响上线

关键路径保护策略：
  └── 关键路径任务优先分配最强资源
  └── 提前识别依赖，主动推进解除
  └── 在关键路径末端设置缓冲（Buffer）
  └── 非关键路径任务可以延期，优先保关键路径
```

## 2️⃣ 跨职能协作

目标：让不同背景、不同目标的人，为同一个产品结果共同努力

### 产品团队协作图谱

```
                    PM
                    │
    ┌───────┬───────┼───────┬───────┐
    │       │       │       │       │
  设计师  工程师  数据师  运营   市场
    │       │       │       │       │
  体验质量 技术实现 数据洞察 用户运营 用户获取
```

PM 与各角色的协作界面

PM × 设计师

```
PM 输入：用户问题、功能边界、验收标准、优先级
设计师输入：交互方案、视觉规范、可用性建议

健康协作信号：
  ├── 设计师参与需求讨论，而非只接受需求
  ├── PM Review「是否解决了正确问题」
  └── 设计师 Review「是否符合设计规范」

常见摩擦点与处理：
  PM 过度干预设计细节 → 回到「用户问题」而非「解决方案」
  设计周期影响开发 → 提前介入，并行而非串行
```

PM × 工程师

```
PM 输入：清晰的需求文档、优先级判断、及时的决策
工程师输入：技术可行性评估、工期估算、技术方案

健康协作信号：
  ├── 工程师理解「为什么做」，不只是「做什么」
  ├── PM 尊重技术判断，不越界指定实现方式
  └── 工期风险提前暴露，不临近上线才告知

建立信任的关键动作：
  └── 保护工程师免受突发需求干扰
  └── 帮助工程师理解业务背景
  └── 为工程师争取合理的技术债偿还时间
```

PM × 数据分析师

```
PM 输入：分析目标、业务背景、决策时间节点
数据师输入：数据可行性、分析报告、指标定义

高效协作原则：
  └── 带着问题找数据，而非「把数据给我看看」
  └── 提前对齐数据口径，避免分析完才发现定义不同
  └── 数据需求优先级透明，让数据师合理排期
```

PM × 业务方（销售 / 运营 / 客服）

```
业务方是用户声音的一线传递者，也是需求的重要来源

与业务方协作原则：
  ├── 定期需求收集会（月度）
  ├── 重要功能提前预告，给业务方准备时间
  ├── 上线后及时同步结果和数据
  └── 建立反馈渠道，而非被动接收投诉

处理业务方需求压力：
  ├── 理解背后的业务诉求（而非直接接受功能要求）
  ├── 透明化优先级逻辑（为什么这个排后面）
  └── 给出预期时间窗口，管理期望
```

### 跨部门协调

RACI 矩阵（明确责任分工）

```
R（Responsible）：执行者，具体做这件事的人
A（Accountable）：负责人，对结果最终负责
C（Consulted）：被咨询者，提供意见和建议
I（Informed）：被告知者，需要知道进展

示例：
                  PM   设计  工程  运营  管理层
需求定义           A    C     C     C     I
界面设计           C    A     C     I     I
技术实现           I    I     A     I     I
运营方案           C    I     I     A     I
上线决策           R    C     C     C     A
```

依赖管理

```
提前识别跨团队依赖（项目启动时）
    ↓
与依赖方确认排期和优先级
    ↓
建立定期同步机制（不要只在 deadline 前联系）
    ↓
依赖风险提前上升（不要等到阻塞才上报）
```

## 3️⃣ 沟通与信息管理

目标：让正确的信息，在正确的时间，到达正确的人

### 沟通层级设计

```
信息分级：
  公开信息（All Hands）→ 全员知晓
  团队信息（Team）    → 核心团队
  决策信息（Leads）   → 管理层
  敏感信息（1-on-1）  → 仅相关人

沟通频率与形式：
  实时：Slack / 飞书（紧急、快速确认）
  异步：文档、邮件（需要思考、正式记录）
  同步：会议（需要讨论、对齐决策）
```

### 会议管理

会议效率原则

```
会前：
  └── 明确会议目标（讨论 / 决策 / 同步）
  └── 提前发出议程和背景材料
  └── 只邀请「必须在场」的人

会中：
  └── 准时开始，准时结束
  └── 指定记录人（不是最低级别的人）
  └── 每个议题聚焦目标，偏题及时拉回
  └── 明确决策，不要「我们再想想」结束

会后：
  └── 30分钟内发出会议纪要
  └── 包含：决策结论 + 行动项 + 负责人 + 截止日期
  └── 行动项在下次会议开始时复盘
```

会议类型与频率

```
1:1（PM × 直属上级）：每周，30-45分钟
  └── 障碍汇报、方向对齐、职业发展

跨职能同步会：每周，30分钟
  └── 进展同步、风险暴露、决策升级

产品评审会：按里程碑，1-2小时
  └── 方案 Review、设计评审、上线决策

季度复盘会：每季度，2-3小时
  └── OKR 回顾、经验总结、下季规划

应该砍掉的会议：
  └── 无议程的例会（改成异步文档更新）
  └── 可以用文档解决的「对齐会」
  └── 超过 8 人的「讨论会」（只适合宣布）
```

### 文档体系建设

产品文档金字塔

```
战略文档（季度更新）
  └── 产品愿景、OKR、路线图

规划文档（月度更新）
  └── Epic 说明、季度计划

需求文档（按功能）
  └── PRD、设计稿、验收标准

过程文档（实时更新）
  └── 会议纪要、决策日志、复盘记录

参考文档（长期维护）
  └── 用户画像、竞品分析、数据字典
```

文档管理原则

```
单一信息源（Single Source of Truth）
  └── 每类信息只存一个地方，避免多版本混乱

文档即沟通
  └── 重要决策写文档，减少「我记得当时说过」

及时更新
  └── 过时的文档比没有文档更危险
  └── 设置文档 owner，定期 Review

可被发现
  └── 好的文档结构 + 搜索友好的命名
  └── 新成员能在 1 天内找到所需信息
```

### 向上管理

管理上级期望的核心原则

```
不要让上级「意外」：
  └── 坏消息早说，比上线前一天说要好
  └── 主动同步风险，不要等被问到

用上级的语言沟通：
  └── 管理层关心：ROI、时间、风险、战略契合
  └── 不要用技术术语或产品细节淹没他们

带着方案而非问题：
  └── 「我们遇到了 XX 问题，我的建议是 A，
       备选方案是 B，需要您决策的是 XX」

定期同步节奏：
  └── 固定的 1:1 比临时汇报效果好
  └── 简短的书面周报比口头汇报更清晰
```

向上汇报结构

```
结论先行（Bottom Line Up Front）：
  └── 先说结论，再说背景和细节
  └── 管理层时间有限，从最重要的开始

一页汇报模板：
  ┌─────────────────────────────┐
  │ 本期进展（完成了什么）       │
  │ 关键数据（核心指标变化）     │
  │ 主要风险（需要关注什么）     │
  │ 下期计划（接下来做什么）     │
  │ 需要支持（请上级帮助什么）   │
  └─────────────────────────────┘
```

## 4️⃣ 个人执行力与 PM 效能

目标：在复杂、模糊、多线并行的环境中，保持清醒的判断和持续的输出

### PM 时间管理

PM 时间分配模型

```
理想分配：
  用户研究 & 发现    20%  ← 大多数 PM 严重不足
  产品规划 & 设计    30%
  跨职能协作 & 会议  25%
  数据分析           15%
  其他（行政、招聘） 10%

现实陷阱：
  └── 会议挤占深度思考时间
  └── 救火消耗规划和研究时间
  └── 「忙碌感」代替了「产出感」
```

时间保护策略

```
深度工作时间块（Deep Work Block）
  └── 每天固定 2-3 小时不被打断的思考时间
  └── 关闭通知，谢绝非紧急打扰

会议集中制
  └── 将会议集中在特定时间段（如下午）
  └── 上午保护为深度工作时间

每周规划仪式
  └── 周五下午：复盘本周、规划下周
  └── 明确下周最重要的 3 件事（Big 3）
```

### PM 决策框架

决策质量提升

```
可逆 vs 不可逆决策：
  可逆（Type 2）→ 快速决策，试错学习
  不可逆（Type 1）→ 慎重决策，充分论证

决策时间管理：
  └── 设定决策截止时间，避免无限拖延
  └── 70% 信息时决策（仅适用于可逆决策，Type 2）
       ├── 不可逆决策（Type 1）不能套用此规则，必须充分论证
       └── 70% 决策必须配套明确的试错上限：
            ├── 最大投入上限（钱、时间、人力）
            ├── 失败信号定义（什么结果算假设证伪）
            └── 退出机制（证伪后如何止损）
  └── 明确「不决策」也是一种决策

避免常见决策偏误：
  沉没成本谬误 → 「已经做了这么多」不是继续的理由
  确认偏误     → 主动寻找反对自己想法的证据
  群体思维     → 鼓励团队说出不同意见
  近因效应     → 最近发生的事不一定最重要
```

### PM 影响力建设

没有直接权力的影响力

```
PM 的影响力来源：
  信息优势 → 掌握最全面的用户、数据、市场信息
  判断力   → 能够做出让团队信服的产品决策
  信任感   → 言出必行，保护团队，公平透明
  愿景感   → 能够描绘清晰的产品方向，让人追随
```

建立团队信任的具体行动

```
对工程师：
  └── 需求清晰，减少返工
  └── 不轻易改需求，改了就承认影响
  └── 帮工程师挡住外部干扰

对设计师：
  └── 给足够的背景，不只给结论
  └── Review 聚焦问题，而非指定方案
  └── 在管理层面前支持设计决策

对业务方：
  └── 承诺的事情做到
  └── 做不到的事情早说，给出替代方案
  └── 定期同步，不让他们有「被忽视感」
```

### PM 的自我成长体系

能力成长三层次

```
执行力（初级）
  └── 按时交付、需求清晰、协作顺畅

判断力（中级）
  └── 正确的优先级、准确的用户洞察、有效的决策

影响力（高级）
  └── 定义方向、建设团队、影响组织
```

PM 成长飞轮

```
做项目（积累经验）
    ↓
主动复盘（提炼规律）
    ↓
输出沉淀（文章、文档、分享）
    ↓
获得反馈（外部视角校正）
    ↓
指导他人（教学相长）
    ↓
回到做项目（更高质量的执行）
```

每周成长习惯

```
读（30分钟）：行业动态、竞品变化、产品案例
思（15分钟）：当周决策复盘，哪里可以更好
写（30分钟）：记录洞察、沉淀方法、输出文档
问（随时）  ：主动向用户、同事、mentor 收集反馈
```
