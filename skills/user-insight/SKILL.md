# 用户洞察：从原始声音到承重假设

## Purpose

评审 $ARGUMENTS（访谈/反馈/观察）。把零散的用户声音提炼成**具体情境下的痛点**与**可证伪的用户价值假设**，而不是模糊的“用户想要更好用”。**目标是让 A 类假设站在证据上，而不是同理心想象上。**

## Context

- 只产出 **A 用户价值** 类假设（商业归 competitor-teardown/后续，技术归 C）。
- 证据等级按来源定：直接访谈/观察 = L3 上限；二手转述 = L2；你的推测 = L1。
- 区分**用户说的**（stated）与**用户做的/情境**（revealed）——后者权重更高。
- **内核回路位置**：本 skill 是回路的**入料口**，只负责把声音变成“带证据的 A 类假设”。你的产出**不是结论**，是待红队的原料——下一站是 `@assumption-xray`，不是方案。

## Instructions

> **动手前先回显当前项目**：先声明 `当前项目: workspace/<slug>/`，确认它就是本次要读写的项目。若同一会话此前在操作别的项目，先提示开新会话或让用户确认切换，再继续。本次所有读写只落在这个目录内。

1. 读 thesis 的 targetUser / coreProblem，作为对齐锚点。
2. 逐条抽取用户声音，标注：情境（何时何地）、任务（想完成什么）、障碍（卡在哪）、现有凑合方案、情绪强度。
3. 聚合成 2–4 个洞察主题，每个配至少一条原始引语/证据。
4. 每个主题转成一条**可证伪的 A 类假设**：`目标用户在[情境]下，因为[障碍]，会[行为/付费]`。
5. 标影响与证据等级（证据等级不得超来源上限）。
6. 指出**证据空白**：哪些是推测、需要再验证。
7. **收尾只交接给内核回路**：新的 A 类假设回写台账后，明确建议下一步 = `@assumption-xray` 对这些假设做红队、点名裸奔假设。**不得建议进入方案/MVP/原型/排期。**

## Output

```
## 用户洞察：[一句话范围]

### 洞察主题（2–4 个）
每个：
- 主题 / 情境 / 障碍 / 现有凑合方案 / 情绪强度
- 支撑证据: [引语或观察]
- 推导出的 A 类假设: [可证伪陈述]

### 证据空白
[哪些还只是推测，需要 direct/data 级验证]

### 下一步（回路内）
交给 @assumption-xray 红队上述 A 类假设 → 点名裸奔 → 每条配最便宜验证
```

## Kernel Write-back

- 每条 A 类假设按 schema 映射，`type: A`，`id` 留空交 validator。
- `provenance.reliability` 据实填（direct/indirect/self），`evidenceLevel` ≤ 上限。
- 直接证据（L3）需 `/review` sign-off；推测（≤L2）自动落库。
- 落库前跑 `node tools/validate.mjs`。

## Notes

- 不要把一次访谈的孤例当成规律；标清样本量。
- 引语原样保留，别润色成你想听的。
- ❌ **不要跳到解决方案 / MVP / 原型 / 排期。** 访谈的产出是“带证据的假设”，不是“可以开工”的信号。假设未经 `@assumption-xray` 红队 + sign-off 前，一律停在“假设 + 最便宜验证”层。
- “下一步”永远指向**内核回路的下一个节点**（红队 / 证据采集 / review），不是产品动作。
