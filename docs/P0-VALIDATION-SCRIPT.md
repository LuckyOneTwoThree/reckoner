# P0 实测脚本 + 留存量表

> Reckoner 自己的承重假设：**「这套内核在真实 PM 手上能跑通，且跨会话能留住」**。在 3 个真实 PM 验证前，所有 Phase 1.5 设计都是"给 0 条数据建组织结构"。本脚本是让触发器从 0 变非 0 的唯一路径。

---

## 实测目标

回答一个问题：**一个 PM 拿到一个想法后，用 Reckoner 跑完一遍内核回路，30 天后还会回来开第二个项目吗？**

不回答：产品对错、功能好坏、UI 满意度——那些是回路外的事。

---

## 实测对象（3 人）

| # | 画像 | 选人标准 |
|---|---|---|
| PM-1 | 有想法、没系统方法论的独立 PM | 照妖镜对他最有用（没被挑战过） |
| PM-2 | 用过 Notion / Linear 管需求，但没假设台账 | 验证回写内核的差异化价值 |
| PM-3 | 资深 PM，有自己的方法论 | 验证 Reckoner 是否"侵入"而非"替代"他已有习惯 |

**避开**：从没用过 AI 的 PM（测的是 AI 适应不是 Reckoner）；只用 AI 当文档生成器的 PM（测不出回路）。

---

## 实测流程（每 PM 一次，约 45 分钟）

### 第 0 步 · 入会（5 分钟）

- 简述 Reckoner 是什么（一句话：「会顶嘴、有记忆的 PM 决策内核」）
- **不演示功能**——避免锚定操作路径
- 让 PM 打开 Claude Code / Codex，加载 Reckoner

### 第 1 步 · 跑回路（30 分钟）

观察 PM 从想法到 `/decide` 的完整路径，记录以下信号：

| 观察点 | 信号 |
|---|---|
| `/new` 填 thesis | 第6格「最致命假设」是自己写还是 agent 引导？ |
| 是否主动跑入料口 | @user-insight / @competitor-teardown 被主动触发还是被推荐？ |
| @assumption-xray 红队 | PM 对红队结果的情绪——接受 / 反驳 / 防御？ |
| @experiment-design | 最便宜验证被写成"实验规格"还是"功能需求"？（后者 = 落地成 MVP 的行动偏误） |
| `/review` sign-off | 是否抗拒给假设标 `validated`？（抗拒 = 纪律生效） |
| `/decide` | go 时是否仍有裸奔承重假设被忽略？ |

### 第 2 步 · 离场访谈（10 分钟）

问 5 个问题，**不引导**：

1. "刚才那个过程，哪里让你不舒服？"
2. "如果下次有个新想法，你会再打开它吗？为什么？"
3. "你平时没这个工具时，这一步是怎么做的？"
4. "哪里你觉得是 agent 在帮你，哪里是它在挡你？"
5. "如果只留一个功能，你留哪个？"

---

## 留存量表（30 天后）

| 指标 | 定义 | 达标线 | 触发动作 |
|---|---|---|---|
| **30 天回访率** | 30 天后是否再次打开 Reckoner 跑任意 skill | ≥2/3 | 若 <2/3，承重假设被反驳，走 @revise-thesis |
| **第 2 项目启动率** | 是否在 Reckoner 里开了第 2 个项目 | ≥1/3 | personal/ 触发条件首次满足 |
| **假设台账填充度** | 平均每项目假设条数 | ≥5 条 | 若 <5，xray 没产出足够假设 |
| **承重假设验证率** | validated/refuted 占承重假设比例 | ≥40% | 若 <40%，回路没跑到 sign-off |
| **裸奔 go 率** | go 时仍有裸奔承重假设的项目比例 | 0% | 若 >0%，铁律被绕过，需收紧 |

---

## 实测纪律

- **不教 PM 怎么用**——只在他们卡住时指向 AGENTS.md 能力清单
- **不解释为什么这么设计**——避免锚定答案
- **不测 UI 满意度**——Reckoner 是 CLI/agent 交互，UI 不是承重假设
- **测完即走，不主动回访**——让留存信号自然发生（主动回访 = 污染留存数据）

---

## 实测后动作

- 达标 → P0 承重假设 validated，Phase 1.5 触发条件开始从 0 变非 0
- 不达标 → 走 `@revise-thesis`，修订 Reckoner 的论点（不是加功能）
